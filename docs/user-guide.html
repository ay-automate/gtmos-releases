GTM OS user guide

Run your go-to-market on GTM OS

GTM OS is a governed system for your revenue team: a CRM, eight engines in the console (Score, Outreach, Performance Ads, SEO & GEO, Enrichment, Merges, Plays and Routing), signals and a research agent. Your coding agent builds and runs it. A person approves anything that touches a customer or goes live, and every factual claim in what you send is checked against proof you approved.

Written for GTM OS release 0.2.5 (CLI 0.2.5). Console paths are written as Group > Page; every page lives under /org/<orgId>/.

QuickstartEmpty folder to a live system in 10 steps, with Claude Code doing the work and a setup wizard in the console. Customize anythingAsk your agent to change engines, the data model, data, integrations and screens. Something broke?Real error messages and the fix for each.

Rules that explain most of what you will see

  • Four-eyes. Whoever proposes a change can never approve it. You need a second person (the approver) from day one.
  • Dev first, then prod. Config your agent writes lands in dev. It goes live only after a person signs it and promotes it to prod.
  • looot for outside data, Composio for your own apps. looot supplies enrichment, emails, lists and intent. Composio connects your CRM, Slack, Search Console and other apps.
  • Dry first, then live. Start in Dry Mode (for the whole organization and for each engine) and see what would have happened before anything real goes out.
Quickstart

From an empty folder to live engines

Claude Code runs the install and the configuration. It stops and asks you only for what a person must do: sign-ins, keys, DNS records and approvals. Plan for about an hour.

  1. Check the prerequisites 5 min

    • Docker Desktop installed and running.
    • 10 GB or more free disk on the drive you install to (images plus database).
    • 4 GB or more free RAM for the stack (Postgres, API, worker, MCP, console). Close heavy apps. On Windows, Docker runs in WSL 2: if containers get killed, raise the memory limit in %UserProfile%\.wslconfig and restart Docker.
    • Node 22 or newer, and Claude Code.
    • The gtm CLI, from npm:
    npm i -g @gtmos/cli
    docker info --format '{{.ServerVersion}}'
node -v
gtm version --offline
    A Docker server version, v22.x or newer, and the gtm CLI version.

  2. Make an empty folder and start Claude 1 min

    mkdir my-gtm && cd my-gtm
claude

    This folder becomes your agent workspace. The GTM OS instance itself goes in a subfolder later.

  3. Run gtm init inside Claude, then restart Claude 1 min

    In the Claude prompt, the ! prefix runs a shell command:

    ! gtm init
    "No GTM OS instance connected yet. Open Claude Code here and run /setup-gtmos". The folder now holds .claude/ (skills, slash commands), .mcp.json and docs/gtmos/.

    Quit Claude Code and start it again in the same folder (claude). Claude reads new commands only at startup.

    • which keys you have ready: a model provider (Anthropic, Gemini or OpenAI; one is required), looot, Resend.

    1. Open the console URL Claude printed (default http://localhost:3000).
    2. Sign in as the owner with GTMOS_OWNER_PASSWORD.
    3. Open a second browser profile (or a private window) and sign in as the approver with GTMOS_APPROVER_PASSWORD. Keep both windows open.
    Mission Control (the home page) in both windows. The approver also sees Settings, because the approver is an admin.

  6. Connect your tools in Integrations > Connections Needs a human

    2. On the Composio card click Connect Composio, sign in to Composio, accept. You come back to the console.
    3. Claude then links your apps. To do it yourself click Sync connected apps: every app already connected in your Composio account appears under Connected apps as ACTIVE.

    You can paste a key to Claude instead and it stores it with connections.create. A key pasted in chat stays in the transcript, so the console is the private option.

  7. Set up and build your system 20 to 40 min

    Two ways in, and you can mix them: the setup wizard in the console (Setup), or your agent with:

    /build-gtm-system
    1. Answer the discovery interview (offer, ICP, signals, personas, regions, channels, CRM, volumes, approver). Pasting a one-page brief saves time. In the wizard these are the cards you review.
    2. Claude recommends the closest blueprint, applies it in dev, then customizes each engine for you. Engines start in Dry Mode.
    3. When Claude says a proposal is waiting: approver window, Approvals, open it, Approve, then Execute.
    Claude reports each engine as built and verified, and lists Open items in .claude/memory/setup-status.md. A banner says "N definitions are in dev, not live".

  8. Go live: sign, promote, approve Needs a human

    Open CRM > Environments. The Go live card is at the top.

    1. Approver window: click Review & sign all proposed (N), read the diffs, confirm. (The owner cannot sign what the owner's agent proposed.)
    2. Owner window: click Promote dev → prod, check the list, confirm. This proposes one approval.
    3. Approver window: Approvals, open the promotion, Approve, then Execute.
    The Go live card reads "Everything is live." and the "in dev, not live" banner is gone.

    Sending email? Activate the lane once it is in prod: Email sending, step 4.

  9. See the engines working 15 min

    • Signals: CRM > Hot list, click Scan for signals now (owner or admin; capped per run).
    • Accounts: CRM > Companies, open one; its Overview shows the score and Why this score.
    • Score: Engines > Score, click Qualify on an account.
    • Workflow: Settings > Workflow automation; the qualified-account handoff and signal reactions are on by default.
    • Outreach: the approver sees proposed messages in Approvals.
    • SEO & GEO: Engines > SEO & GEO, open the page workbench link, Site visibility, click Run visibility.
    • Search: Settings > Search index, click Reindex now.
    • Agent: open a company, Agent tab, ask "Why is this account a fit for us?".

  10. Run the go-live check 5 min

    /go-live-check
    One line per check marked GO, NO-GO or N-A with its evidence, then one overall result. NO-GO comes with an ordered list of fixes.

    Your first-win checklist on Home shows the same journey as eight milestones computed from what really happened in your workspace.

Prefer to do it by hand?

Goal: install an instance and connect an agent workspace without /setup-gtmos. Commands are bash; on PowerShell use $env:NAME = "value" instead of export.

  1. Install the instance into its own folder (owner plus approver; passwords are generated into its .env): 
    gtm setup gtm-instance --org "Acme" --email you@acme.com --approver-email cofounder@acme.com
    Port busy? Add --console-port, --api-port, --mcp-port or --postgres-port. Local images only? Add --version <tag> --no-pull. The ports bind to 127.0.0.1 unless you add --bind <address> (see Self-host on a server).
  2. Sign in as the owner (it prompts for the password, or reads GTMOS_PASSWORD). Your org id is ORGANIZATION_ID in gtm-instance/.env. 
    export GTMOS_API_URL=http://127.0.0.1:3001 GTMOS_ORG=<org id>
gtm login --email you@acme.com --console-url http://localhost:3000
    Run the export GTMOS_TOKEN=... line it prints.
  3. Create the agent key (shown once): 
    gtm token create --name claude-code --client claude-code --preset full-gtm-engineer --expires-days 90
  4. Put the key in GTMOS_AGENT_TOKEN (per OS), then connect your workspace folder and check: 
    gtm init --url http://127.0.0.1:3001 --key <agent key> --yes
gtm doctor
  5. Start claude in the workspace and run /mcp.
gtm doctor prints one line per provider (LIVE, UNVERIF, FAILED, FIXTURE or MISSING) with the remediation for each.
How-to

How-to guides

Each guide: the goal, the steps, what you should see, and the common errors. Needs a human marks steps your agent cannot do for you.

Accounts and team

Goal: the right people with the right roles, including a second approver.

RoleCan do
owner, adminEverything, including approve, reject and execute proposals. Only these roles approve.
memberRead and write records. Cannot approve or change settings.
builderDelegated agency role: everything except approve.

There is no read-only viewer role.

  1. Settings > Members, Invite a member: email, role (member, admin or owner), Invite. Pending invitations are listed below.
  2. Or provision a verified teammate from a terminal (run it yourself, so your agent never sees the password): 
    gtm member add --email approver@acme.com --password '<password>' --role admin --org <org id>
  3. Stop an agent everywhere: Settings > Agents, Kill. Revive it there later.
  4. Agencies: Settings > Delegations lists access granted to an agency org; revoke it there.
At least two people with owner or admin. Without a second one, nothing your agent proposes can go live.
Common errors
  • Role "member" does not hold action.approve: ask an owner or admin.
  • "An action proposed by your own agent must be approved by a different person": you created the agent key, so a second admin approves.

Composio: connect your own apps Needs a human

Goal: GTM OS can read and act in your CRM and other SaaS apps. Composio is never used to buy data.

  1. Integrations > Connections, Composio card, click Connect Composio (recommended: OAuth sign-in, tokens refresh on their own).
  2. Prefer a key? Click Advanced: paste a Connect key ck_... (connect.composio.dev) or a project key ak_... (platform.composio.dev, project, Settings, API Keys). The key is verified live before it is saved. One Composio credential per org; the last one saved wins.
  3. Click Sync connected apps: apps already connected in your Composio account become ACTIVE; apps no longer connected become inactive.
  4. A new app: search the App catalog, click Connect, finish the hosted sign-in (the link lasts about 10 minutes).
  5. Several accounts for one app? Next to the app click Use an existing connection, then Use this on the right one.
  6. CRM of record section: pick HubSpot, Salesforce, Pipedrive, Attio or Zoho, then Sync now. It also syncs every 6 hours.
  7. Any other app: on the connected app click Map to ontology (see Bring data in).
"Signed in to Composio", your apps listed as ACTIVE, and under CRM of record a Last sync with counts.
Common errors
  • "This is a Composio user API key (uak_...) ... Nothing was saved.": use Connect Composio, a ck_ or an ak_ key.
  • AUTH_EXPIRED "Composio sign-in expired or was revoked": click Reconnect Composio.
  • "Composio: hubspot is not connected for this organization": connect it on the card, then check it reads ACTIVE.
  • App stuck INITIATED or EXPIRED: the sign-in link timed out; click Reconnect.
  • A project key (ak_) sees only its own developer project, not apps connected in Composio Connect.
  • Pipedrive, Meta Ads, LinkedIn Ads, Webflow and some others need your own auth app in Composio ("Needs your own auth app").

API keys: model, looot, email

Goal: a model provider and looot are live (and Resend if you send through it).

  1. Integrations > Connections, Add a connection.
  2. Provider: anthropic, gemini or openai (at least one), looot, resend. Give it a label, paste the key, add it.
  3. Run Test on the new connection. A stored but untested key reads "Stored, not verified".
Required connections shows the provider as Connected. Keys are live at once, with no restart.

Semantic search needs an OpenAI or Gemini key (Anthropic has no embedding model). Without one, search is full-text only.

Common errors
  • Do not put keys in instance/.env after install: env changes apply only when containers are recreated.
  • looot 402 insufficient_balance: top up your looot balance.

  2. Choose Google or Microsoft, tick the features (Read mail, Send mail, Calendar; Google also Search Console, Google Ads), connect and accept the consent screen.

  4. Ask your agent to set the Search Console property, or give it: sc-domain:acme.com or https://www.acme.com/.

Email sending: domain, lane, mailbox

Goal: real emails can go out, only through an approved lane and a bound mailbox.

  1. Sender. Best: a Gmail or Microsoft 365 account with Send mail in Settings > Connected accounts. Otherwise a resend connection (verify your domain in Resend first).
  2. DNS Needs a human: at your DNS host add SPF (one TXT starting v=spf1), DKIM (the record your provider shows at <selector>._domainkey.<domain>) and DMARC (TXT at _dmarc.<domain>, for example v=DMARC1; p=none; rua=mailto:dmarc@<domain>). Check: 
    nslookup -type=TXT acme.com
nslookup -type=TXT _dmarc.acme.com
  3. Lane. Your agent writes the lane (definition.lane: daily cap, sending domain, sender postal address, budget). Sign and promote it (Environments).
  4. Activate the lane. Engines > Outreach, open the Outreach workbench link, Sending lanes, click Activate lane (optional DKIM selector). Or: 
    gtm lane activate <laneKey> --env prod
    A different person approves and executes it in Approvals.
  5. Mailbox. Bind it when you send: pick it in Sending mailbox on the workbench or on a new sequence.
The activation result shows SPF, DKIM and DMARC checks. In prod all three must pass. New mailboxes warm up (20 a day, +20 a day, up to 200).
Common errors
  • lane_required "refusing an un-laned email send": pick a sending lane, and activate it first.
  • mailbox_required: connect a mailbox with Send mail and pick it.
  • mailbox_daily_cap: wait, or add mailboxes.
  • "lane ... envelope budget exhausted ... re-approval required": activate the lane again, or raise its budget.
  • Lane activation refused in prod: fix DNS, activate again.

LinkedIn through Unipile Needs a human

Goal: read LinkedIn profiles, inbox and connections, and send LinkedIn steps through the same approval path as email.

  1. Integrations > Connections, Unipile (LinkedIn sending) card.
  2. Fill API key, DSN (your account's API host, for example api8.unipile.com:13814) and optionally the LinkedIn account id.
  3. Click Save and test.

A real Unipile account is required, and live sending is not yet verified against one in this release.

Add your own MCP server

Goal: an internal tool becomes a data source or capability for GTM OS (the opposite direction from your agent's MCP).

  1. Integrations > Connections, MCP servers card, Add an MCP server: server name (lowercase), server URL (a streamable-HTTP endpoint, usually ending /mcp), optional auth header name and value. Credentials go in the header, never in the URL.
  2. Test it: the tool catalog loads.
  3. Needs a human Mark each tool Read or Write (approval). An unmarked tool cannot be used.
  4. Ask your agent to bind a capability to it, or map its records (see example prompt).
The server marked Connected with its tools listed.
Common errors
  • "initialize failed ... did not answer with a JSON-RPC result": the URL is not an MCP endpoint (often missing /mcp).
  • FORBIDDEN "no declared effect": mark the tool Read or Write.

Required connections and readiness

Goal: know what is live and what is missing.

  1. Top of Integrations > Connections: Required connections. States: Connected, Stored not verified, Failed, Required: missing, Not connected, Not needed.
  2. From a terminal: 
    gtm doctor --strict
Exit code 0 with --strict means every needed item is live. A model provider is always required; looot while you use Signals or Enrichment; a sender while you use Outreach; Search Console while you use SEO & GEO. An applied blueprint makes its declared connections required.

Connect Claude Code, Codex or any MCP agent

Goal: your agent talks to GTM OS through MCP with its own key, acting for you.

  1. Settings > Developer, Connect Claude Code / Codex: choose the Coding agent (Claude Code, Codex or Other MCP client), an Agent name, Preset: Full GTM engineer, then Create agent key. Copy the key now: it is shown once. The page also shows the org id, the MCP endpoint and setup snippets.
  2. Or from a terminal with your owner session (gtm login first): 
    gtm token create --name claude-code --client claude-code --preset full-gtm-engineer --expires-days 90
  3. Put the key in your environment, never in a file.

    Windows PowerShell (persistent; then open a new terminal):

    [Environment]::SetEnvironmentVariable('GTMOS_AGENT_TOKEN', '<agent key>', 'User')

    macOS / Linux: add this line to ~/.zshrc or ~/.bashrc, then open a new terminal:

    export GTMOS_AGENT_TOKEN='<agent key>'
  4. In your workspace folder, connect it to the instance (writes .mcp.json with Bearer ${GTMOS_AGENT_TOKEN}, AGENTS.md for Codex, .claude/ and docs/gtmos/): 
    gtm init --url http://127.0.0.1:3001 --key <agent key> --yes
  5. Restart the agent in that folder. In Claude Code run /mcp.
  6. Later, pull fresh docs, skills and subagents from your live org (files you edited are kept): 
    gtm init --refresh --yes
/mcp lists gtmos as connected. The agent's first call is usually gtm_describe.

Common errors
  • UNAUTHORIZED "No valid session or agent token": the variable is missing, wrong, revoked or expired (keys default to 90 days). Create a new key, set it, restart.
  • MCP tools fail after an upgrade or restart of the stack: run /mcp to reconnect.
  • "This agent key does not hold the "engine.configure" scope": create a new key with the Full GTM engineer preset.
  • "GTMOS_TOKEN holds an API key. Keys cannot mint keys": use gtm login and its session token.
  • gtm init warns that .mcp.json held a literal key: it rewrote it; revoke that key (gtm token revoke <key-id>) and use a fresh one.

Setup wizard Needs a human

Goal: turn what your company already knows (answers, website, connected data, documents) into the definitions your engines run on. Nine steps on six screens. Open Setup in the console. Your agent can run the same steps over MCP (say "set up GTM OS for my company") and you can take turns: what one saves, the other sees.

ScreenStepsYou do
1. WelcomeCompany, MotionCompany profile, team size, an optional private ARR band, markets, motions, your stack, up to three pains and a few free answers, hours a week. Pick the engines and a blueprint (the suggestions show the facts they rest on).
2. Connect your dataConnectionsSee real coverage per source, connect sources, Pull now, and send access requests to the people who hold the keys. Each missing grant becomes a numbered open ask.
3. Your definitionsDefinitionsUpload setup documents (ICP notes, stage definitions, pricing, brand voice, suppression lists, a DPA). Review each drafted card with its evidence: edit, skip or approve.
4. Rules and who approves whatRules, TeamBuying roles, consent per channel, trust rules (Dry Mode, caps, quiet hours), autonomy per engine, seats and role profiles.
5. The buildBuildCheck engine readiness, run the build, follow its live log, clear what waits for a human.
6. First motion and 90 daysPlan, LaunchShape the 90-day plan, refresh the operating-system brief, preview and run Launch.

Rules that hold on every screen

  • No invented values. Every suggestion shows the facts it rests on: an answer you gave, a page of your site, a document, a real count from a connected source. A value nobody knows yet stays empty and becomes a numbered open ask with an owner. With no model configured the page says so and fills only what the data supports.
  • Every saved answer changes engine behavior. A card is published through the operation that owns that definition, with the same permissions, approvals and audit as anywhere else.
  • The proposer never approves. Change sets, journeys, blueprints and promotions are approved by a different person in Approvals. Definitions are signed by someone other than the proposer.

Good to know

  • Documents: PDF with text, Word, Excel, CSV, JSON, Markdown and text, up to 10 MB each and 50 per organization. Scanned PDFs and images are refused with the reason. Suppression lists, a DPA and any file with emails or phone numbers are restricted: only owners and admins read their text, and they are never sent to a model.
  • The ARR band is private: only a human owner or admin sets or reads it, and it is hidden from agents.
  • Cards approved on screens 3 and 4 land in dev. Launch is human only: it signs and promotes the setup definitions and turns an engine live only where its autonomy card says so.
  • Seats narrow what a role may do and never widen it. Never put the sole owner in the Operator or Exec seat. GTM OS refuses any change that would remove the last person who can still run the build, approve cards and launch.
  • If the wizard says someone else changed the session, re-read it and redo the step.
Setup shows every step done, the build log ends with "ready", and the first-win card lights up its first milestones.
Common errors
  • A card is refused with a list of issues (for example an ICP with no rules and no closed-won deals): fill it with your own criteria, or skip it for now.
  • The revenue card offers only connected revenue sources. With none, it opens the ask "Connect a CRM with deals or Stripe".
  • The do-not-contact card is empty after an agent drafted the cards: an owner or admin redrafts it, because only they can read the restricted documents.

Build your GTM system with your agent

Goal: a full, customized setup from one conversation.

  1. Run /build-gtm-system (optionally with a goal, for example /build-gtm-system B2B SaaS sales-led, outbound + SEO).
  2. Answer the discovery interview, asked in batches: business and offer, ICP and tiers, personas, markets and compliance, channels, CRM and tools, data volumes, team and approver.
  3. Claude reads the live state, recommends the closest general blueprint with a reason, and applies it in dev.
  4. Engine by engine (data first, then Score, routing and plays, then Outreach, SEO & GEO, Ads), it explains, shows defaults, asks only what matters, writes the definitions, and verifies live.
  5. You approve proposals (approver window), then go live with sign and promote.
Each engine reported as verified, decisions in .claude/memory/decision-records.md, and human tasks as Open items in .claude/memory/setup-status.md.

Blueprints you can start from: b2b-saas-sales-led, enterprise-abm, b2b-saas-plg, devtools, agency-services, b2b-marketplace, dtc-b2c, and the starters outbound, seo, full-gtm (the last two require Search Console). Browse them in CRM > Blueprints, View & apply.

First wins and operator nudges

Goal: always know the next useful step, based on what really happened in your workspace.

  1. Open Home or Setup. The first-win card lists eight milestones: the instance is ready, a real data source is connected (not a fixture), the first sync finished, a person signed the first definition, the first Dry Mode draft was produced, accounts have fit scores, a second person approved a proposed action, and the first live message went out.
  2. Each open milestone says what to do next. A fact GTM OS cannot read reads "unknown", never a guess.
  3. Ask your agent "what is my next first-win step?" for the same answer.
Milestones turn done only from real events (an executed operation, a live connection, an approval), never from clicks.

Operator nudges

  • Owners and admins get an in-app nudge when something needs them.
  • Email is opt-in. Each person turns it on in their own notification preferences. Every email carries a signed unsubscribe link that works without signing in, and nobody gets more than one a week.
  • If email is not configured on the instance, the nudge says so plainly instead of pretending it was sent. gtm doctor shows the email transport as an optional line.
  • An owner or admin can invalidate every earlier unsubscribe link (notification.preferences.revoke_links, a human-only operation).

Does your harness match?

gtm init records which CLI, which skills release and which operation list it generated your project files from. gtm doctor compares that with what is running and reports a stale harness with the fix: gtm init --refresh. A project created before 0.2.5 reads "unstamped", which is informational.

  2. Per engine. Proof library and claims Needs a human

Goal: nothing you send states a fact you cannot back up.

  1. Settings > Proof library, add proof: case studies, metrics, testimonials and logos. Give each a permission (public, anonymized or internal only) and an optional expiry.

  3. A second person activates each proof (four-eyes). Customer phrases mined from your calls, replies and won deals are approved one by one.

Environments and going live

Self-host on a server

Goal: people reach GTM OS at https://app.acme.com while the instance stays closed to everything except your proxy.

Changed in 0.2.5. The console (3000), API (3001) and MCP (3004) ports, like Postgres, bind to 127.0.0.1 by default. An existing deployment becomes local-only on its next gtm up or gtm upgrade. If you only use GTM OS on one machine, nothing changes for you.
GTMOS_BIND_ADDRESSMeaning
127.0.0.1 (default)Reachable from this machine only. Use it with a reverse proxy on the same machine.
0.0.0.0Reachable on every network interface. Only behind a firewall that allows exactly the ports you intend.
A private IP such as 10.0.0.5Reachable on that interface only, for a proxy on another host in the same private network.

Put a reverse proxy in front (recommended)

  1. DNS and firewall Needs a human: point app.acme.com (console), api.acme.com (API) and, if coding agents outside the server need it, mcp.acme.com at the server. Use one parent domain so the login cookie is shared. Open only ports 80 and 443. Do not open 3000, 3001, 3004 or 5432.
  2. Keep GTMOS_BIND_ADDRESS=127.0.0.1, and set the public URLs in .env (the origins a browser really uses, with https:// and no trailing slash), then run gtm up again: 
    PUBLIC_API_URL=https://api.acme.com
PUBLIC_CONSOLE_URL=https://app.acme.com
PUBLIC_MCP_URL=https://mcp.acme.com
  3. Proxy each host to its local port. With Caddy (it gets and renews the HTTPS certificates) the whole Caddyfile is: 
    app.acme.com {
    reverse_proxy 127.0.0.1:3000
}

api.acme.com {
    reverse_proxy 127.0.0.1:3001
}

mcp.acme.com {
    reverse_proxy 127.0.0.1:3004
}
    nginx works the same way: one server block per host with proxy_pass to its local port, the Host and X-Forwarded-Proto headers, and the Upgrade headers for the console.
  4. Check it: 
    curl https://api.acme.com/health
curl -I https://app.acme.com
ss -tlnp | grep -E ':(3000|3001|3004|5432)\b'
The health call answers ok, the console answers 200 or redirects to the login page, and every line of the last command shows 127.0.0.1, never 0.0.0.0 or *.

Open the ports on purpose instead

Edit GTMOS_BIND_ADDRESS in .env and run gtm up again, or create the instance with gtm up --bind 0.0.0.0. gtm up rewrites docker-compose.yml on every run, so never edit the compose file to open or close ports. The .env value is kept across runs. A --bind flag passed to an existing instance is ignored and reported, because the existing .env wins.

Upgrading an older instance

The first gtm up or gtm upgrade on 0.2.5 prints a warning when your .env has no GTMOS_BIND_ADDRESS, and writes 127.0.0.1 into it so the choice is explicit from then on. If a teammate's browser, a webhook or an MCP client on another machine was reaching the instance by IP address, choose a reverse proxy or 0.0.0.0 as above.

Common errors
  • Login redirects loop or cookies are not stored: the public URLs in .env do not match what the browser uses (for example http:// in .env and https:// in the browser).
  • Nothing answers by IP address after an upgrade: the ports are local-only now. See above.

Upgrade GTM OS

Goal: move your instance to a newer release without losing anything. An upgrade never touches, removes or loses your data. Every release only adds (new tables, nullable or defaulted columns, indexes). The updater refuses any release that does not, and there is no override.

Which version am I on?

The CLI version and the instance version are separate things. gtm upgrade --check shows both, plus what the signed release list offers, and changes nothing. Releases before 0.2.5 published images only as 0.2.2 and stable. CLI versions 0.2.3 and 0.2.4 shipped no images, so an instance installed with either still runs the 0.2.2 images.

  1. Upgrade the CLI first. It renders the compose file your instance runs on, so it must be at least as new as the release you move to. If it is too old, gtm upgrade stops and tells you which version to install. 
    npm i -g @gtmos/cli@latest
  2. See what is available (from the instance folder, or add --dir <path>): 
    gtm upgrade --check
  3. Rehearse. It prints every command and changes nothing: 
    gtm upgrade --channel stable --dry-run
  4. Upgrade. --yes is required because it migrates your live database: 
    gtm upgrade --channel stable --yes
  5. In Claude Code run /mcp to reconnect, then refresh your project files in each project folder: 
    gtm init --refresh
A plain gtm upgrade never moves a pinned install. With neither --channel nor --to it only re-pulls and re-verifies the release you already run. To move, choose the target on purpose: --channel stable, or --to <version> for an exact release.

What happens, step by step

  1. The signed release list is fetched and its signature checked. The path is planned by its rules: no downgrade, no skipped required stop, additive-only releases, a minimum CLI. Any failed check refuses the upgrade before anything is pulled.
  2. Preflight: one update at a time, and free disk at least twice the database size plus 2 GB.
  3. The target images are pulled, and each digest must match the signed digest.
  4. The additive-only guard reads every pending migration and refuses anything that drops, renames, retypes, deletes or overwrites.
  5. The API, worker, MCP and console stop gracefully. A backup is taken and read back to verify it.
  6. A rehearsal restores that backup into a scratch database, migrates it and compares it with your live data (tables, columns, types, row counts, row checksums). Any difference refuses the upgrade.
  7. The version is pinned in .env, the migration runs inside the new image, services start, and health and schema are verified. The newest five backups are kept.

What is preserved

  • All your data: records, history, definitions, approvals, connections and keys.
  • Your apps and configuration. An upgrade changes no installed engine app. See Packages for engine app updates.
  • Your GTMOS_MASTER_KEY. Backups do not contain it. Keep it safe, apart from the dump.

Rollback

A failed upgrade rolls back by swapping the images back: the previous compose and .env files and the previous images are restored and the services restart on them. The database is never restored, dropped or recreated by an upgrade, and the verified backup is kept. This works because every migration is additive, so the previous code runs on the migrated database.

Restoring a backup is a manual last resort, for example if something other than the upgrade damaged your data. Never restore over the live database: rename it first, then restore into a new one. gtm upgrade --help prints the exact commands.

Moving to 0.2.5 from 0.2.2 (or CLI 0.2.3 or 0.2.4 on 0.2.2 images)

  • Upgrade the CLI first. This is not optional.
  • Ports become local-only. See Self-host on a server. If people or systems reach the server by IP address, choose a reverse proxy or GTMOS_BIND_ADDRESS=0.0.0.0.
  • Read Security defaults: GTMOS_LIVE, instance keys, CSV import permission, private records.
  • Account scores can move once on the first rescan (preview it). Visits from AI assistants move from "Website (other)" to SEO & GEO credit. New workspaces start with the signal verification gate on Strict.
  • Run gtm init --refresh in each project folder for the new skills and subagents.
  • You are already on a newer 0.2.x? The path is the same. If a release in between is marked as a required stop, gtm upgrade plans it as an extra hop and takes a backup at each hop.

Check it worked

  1. gtm doctor shows the sources you expect as live, and its Harness section has no stale line.
  2. GET /health reports the new version on the API, worker, MCP server and console.
  3. The upgrade reported that verification passed, and a snapshot exists in your backups folder.
  4. Row counts of your main tables match what you noted before.
  5. A rescan preview looks reasonable before the first rescan.
  6. Dry Mode send check: propose one send to an internal address and confirm that a different person has to approve it.
  7. Settings > Proof library: add one proof and check the claims check passes and blocks as expected.

With the updater service installed (gtm updater install), instance admins can also update from Settings > Updates.

If something looks wrong
  • The upgrade refused before changing anything: read the message. It names the failed check (signature, path rule, CLI too old, disk, a non-additive migration).
  • It failed part way: the images were swapped back and your backup is in the backups folder. Run gtm doctor and GET /health to confirm what is running.
  • You need data from a backup: follow the manual steps in gtm upgrade --help, and do not skip renaming the live database.

Reference

Glossary

Operation
One capability (for example score.score_account). Console, CLI, API and MCP all call the same operations. Classes: Q read, D data write, T stage change, E customer-facing effect, M config.
Engine
An installed package that does one GTM job. Eight appear in the console: Score, Outreach, Performance Ads, SEO & GEO, Enrichment, Merges, Plays and Routing. Signals and the research agent support them.
Definition
Versioned config an engine reads: scoring model, lane, play, binding, source mapping, segment, persona.
Blueprint
A general template that seeds a whole motion (definitions, plays, lanes, metrics) in one change.
Package
Anything installable: engines, screens, connectors, ontology modules, blueprints.
Ontology
The data model: built-in gtm.* objects plus your custom fields and custom.* objects.
Proposal / approval
A pending action that runs only after another person approves and executes it.
Four-eyes
The proposer, and the person whose agent proposed, can never approve, sign or execute it.
Environment
dev, staging, prod. Runtime reads prod.
Sign / promote
A person signs a definition in dev; promoting copies signed versions up to prod.
Lane
A sending channel with caps, checks, budget and domain. Every send needs an activated lane.
Agent key
A gtm_... key your agent uses. It acts for you and can never approve.
Dry Mode
A switch that turns customer-facing actions into drafts. It exists for the whole organization and for each engine, and the stricter one applies.
Claims gate
The check that every factual claim in outbound content is backed by active proof, when an action is proposed and again before it runs.
Proof library
Your approved case studies, metrics, testimonials and logos, each with a permission and an optional expiry.
First win
One of eight milestones, computed from real events, that shows how far your workspace has come.
Harness
The files gtm init writes in your project (skills, subagents, commands, MCP config, docs) so your agent can run GTM OS.
looot
The third-party data provider: enrichment, emails, phones, lists, intent, SEO keyword data.
Composio
The bridge to your own apps: CRM, Slack, Typeform, Search Console, Ahrefs and more.
Source mapping
A signed rule that maps any app's records into GTM OS objects.
Readiness
The live status of every connection: live, stored not verified, failed, fixture, not configured.
Demo vs live mode
Demo serves fake fixture data where a key is missing. Live fails with NOT_CONFIGURED instead. Real go-live needs live mode.

Known limitations and what is not in this release

Plan around these before you promise them to your team.

Not built yet

  • Create in CRM. There is no gated "create a record in the CRM" action. CRM writes stay update-only, and high-risk Composio writes need per-record approval.
  • Custom field display and filters. "Show in tables" and "Allow filtering" on a custom field are stored, but the Companies list has no such columns or filters yet. Record filters over the API and MCP do work.
  • Company context for AI steps. Only brand voice, proof and customer phrases reach drafts. The rest of your company context does not yet.
  • Connectors without a native card: Instantly, lemlist, Smartlead, Gong, Mixpanel and Amplitude. Use Composio.
  • Deferred engines and features: new engines (ABM, sales intelligence, lifecycle, reporting); the ads creative loop, audience sync and offline conversions; routing SLAs and escalation; merge batches and learning from rulings; an enrichment catalog with triggers for job changes; play holdouts and a larger play library; GEO gap fixes and a link graph; more vendor skill packs; engine-dependent agents and per-agent evaluation sets.
  • White-label (custom branding or domain per client) is not available. Agencies use delegations.
  • Expansion and reorder for existing customers is not a shipped motion. Your agent can compose a custom segment and play, and renewal runway ships as a play.
  • No DNS operation: lane activation checks SPF, DKIM and DMARC, but you add the records at your DNS host.
  • There is no viewer role.

Works, with a caveat

  • Signal scan quality. Web search results are not yet checked as being about the account. Set up a news binding for better results, or switch the scan off.
  • LinkedIn sending is high risk for your account, needs your explicit acceptance and a real Unipile account, and is not yet verified live.

Rough edges

  • The Records and Model pages still list ontology keys and type names, because they are model-builder pages.
  • A few small icon buttons are under 28 px wide at phone width.
  • Derived and metric lineage is empty, and relationship cardinality is recorded but not enforced.

Needs a live check with real accounts

The code is tested against contracts and a live database, but treat these as unverified until you have checked them with a real account:

  • Unipile: a LinkedIn message, a connection request and the accept wait.
  • Webflow and WordPress.com publishing through Composio, and self-hosted WordPress through the signed webhook.
  • Gmail: a real bounce report arriving in a connected mailbox.
  • Resend: send, bounce and complaint events.
  • Salesforce: the native adapter is not verified against a real organization. Use the Composio path.
