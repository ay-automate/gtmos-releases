GTM OS engineer guide

Build and customize GTM OS by talking to Claude

This guide is for the person who sets up GTM OS for a company and keeps tuning it. You work with Claude Code or Claude Desktop, the gtm command line and the console. You change engines and business logic by writing prompts. Two people approve what goes live.

Written for GTM OS release 0.2.5 (CLI 0.2.5). Console paths are written as Group > Page; every page lives under /org/<orgId>/.

  • Prompts are in dark boxes with a Copy button. Replace anything in <angle brackets>.
  • Claude does names the operations Claude calls. You do says what a person must do.
  • Needs a human marks a step Claude cannot do for you.

Rules that explain most of what you will see

  • Claude proposes. A different person approves. The person who proposes can never approve, sign or execute. You need a second approver from day one.
  • Dev first, then prod. Definitions Claude writes land in dev. They go live only after a person signs them and promotes them to prod.
  • Dry first, then live. A new organization starts with every engine in Dry Mode. You switch an engine live on purpose, in Settings > Safety.
  • Definitions are the business logic. Scoring, routing, sequences and voice are signed, versioned documents, not hidden settings.

Chapter 1

The mental model for a GTM engineer

You build your go-to-market system by talking to Claude. Claude works through one door, the GTM OS MCP server. Everything it does is an operation. Anything that goes live or touches a customer waits for a second person to approve it.

The model in one minute

Goal: know what happens between "you ask" and "it is live", so you can predict what Claude will do and where it will stop.

  1. You say what you want in plain words.
  2. Claude looks up the exact operation (with the gtm_describe tool) and calls it with its own agent key. The key acts for you but is never you.
  3. Reads and internal changes run at once. A change that goes live, or anything aimed at a customer (a send, a CRM write, a merge, a page change, an ad budget change), becomes a proposal.
  4. A different person with the owner or admin role approves the proposal in the console (Approvals), then executes it. Needs a human
  5. GTM OS writes down who proposed, who approved and what ran. You can read that trail in Settings > Audit log.
Claude's report names the operation, the environment it used, and an approval id when something is waiting. If it does not name them, ask for them.

Claude never approves anything, and neither can you for what your own agent proposed. This rule is called four-eyes. It is the reason you need a second approver from day one (see Approvals and four-eyes).

Four safety rules that explain most of what you will see

  • Four-eyes. Whoever proposes a change can never approve it. For an agent's proposal, the person the agent acts for cannot approve it either. A second owner or admin must.
  • Dev first, then prod. Every organization has dev, staging and prod. prod is the default: a call that names no environment runs in prod. Definitions cannot be published straight into prod. They are written in dev, signed by a person, then promoted. Customer-facing effects in dev and staging are recorded but not sent.
  • Dry first, then live. Dry Mode (Settings > Safety) turns every customer-facing action into a draft across the whole organization. Each engine also has its own mode, dry or live, and in a new organization every engine starts dry until a person flips it.
  • Never fake data. A value with no source is shown as unverified. Fixture data in a demo instance is marked as fixture. Claude must tell you when a check is not green.

The working loop

Goal: one loop you repeat for every change, whatever the engine.

  1. Describe. Claude reads the operation or definition kind it is about to use.
  2. Change in dev. Claude writes the change to dev and says so.
  3. Propose. Claude reports the approval id and stops. Needs a human
  4. Approve and sign. A second person approves, then signs the definition. Needs a human
  5. Promote. One approval promotes everything from dev to prod (CRM > Environments, the Go live card). Needs a human
  6. Verify. Claude reads the result back and shows you the proof, for example a record, a score reason or a readiness line.

The build chapters go through each step in detail. For now, remember the sentence Claude should end with after any definition change: "I wrote X in dev. It is not live until it is signed and promoted."

Chapter 2

Install and connect Claude

Two jobs: put a GTM OS instance on your machine, and connect Claude to it with its own key. Claude Code does most of the work for you. Claude Desktop can connect too, with limits.

Check the prerequisites

Goal: a machine that can run the stack and a working gtm command.

  • Docker Desktop, installed and running.
  • 10 GB or more of free disk (images plus database).
  • 4 GB or more of free RAM for the stack (Postgres, API, worker, MCP, console). On Windows, Docker runs in WSL 2. If containers are killed, raise the memory limit in %UserProfile%\.wslconfig and restart Docker.
  • Node 22 or newer.
  • Claude Code.
  • The gtm CLI from npm:
npm i -g @gtmos/cli
docker info --format '{{.ServerVersion}}'
node -v
gtm version --offline
A Docker server version, v22.x or newer, and the gtm CLI version.

Make a workspace and run gtm init

Goal: an empty folder that Claude Code can work in, loaded with GTM OS skills, slash commands and the MCP entry.

  1. Make a folder and start Claude Code in it: 
    mkdir my-gtm && cd my-gtm
claude
  2. Inside Claude Code, the ! prefix runs a shell command. Run: 
    ! gtm init
  3. Quit Claude Code and start it again in the same folder. Claude reads new slash commands and skills only at startup.
The output ends with "No GTM OS instance connected yet. Open Claude Code here and run /setup-gtmos" and "Restart Claude Code in this folder so it loads the new commands and skills". The folder now holds CLAUDE.md, AGENTS.md, .mcp.json, .claude/ (subagents, slash commands, skills, memory seeds, settings) and docs/gtmos/ (guides and a generated reference).

With no instance yet, gtm init never fails. It scaffolds offline and tells you what to do next. If an instance already answers on this machine at http://127.0.0.1:3001, it says so.

The key is never written to a file. .mcp.json holds Bearer ${GTMOS_AGENT_TOKEN}, a reference to an environment variable, not the key. If gtm init finds a literal key in .mcp.json it rewrites the entry, warns you, and you should revoke that key.

The same thing by hand

Goal: install an instance and connect a workspace without /setup-gtmos. Commands are for bash. On PowerShell, write $env:NAME = "value" instead of export NAME=value.

  1. Install into its own folder. The owner and approver passwords are generated into its .env: 
    gtm setup gtm-instance --org "Acme" --email you@acme.example --approver-email cofounder@acme.example
    Port busy? Add --console-port, --api-port, --mcp-port or --postgres-port. Local images only? Add --version <tag> --no-pull.
  2. Sign in as the owner. It asks for the password, or reads GTMOS_PASSWORD. Your org id is ORGANIZATION_ID in gtm-instance/.env: 
    export GTMOS_API_URL=http://127.0.0.1:3001 GTMOS_ORG=<org id>
gtm login --email you@acme.example --console-url http://localhost:3000
    Run the export GTMOS_TOKEN=... line it prints. This is your owner session. It is not the agent key.
  3. Create the agent key. It is shown once: 
    gtm token create --name claude-code --client claude-code --preset full-gtm-engineer --expires-days 90
  4. Put the key in your environment (next section).
  5. Connect the workspace and check it: 
    gtm init --url http://127.0.0.1:3001 --key <agent key> --yes
gtm doctor
  6. Start claude in the workspace and run /mcp.
gtm init prints numbered steps. Step 2 reads like key OK: agent "claude-code" · org <id> · scopes record.read, record.write, engine.configure, connection.manage · cannot approve. The last block says Readiness: GO or NO-GO with one line per blocker. gtm doctor prints one line per provider with the tag LIVE, UNVERIF, FAILED, FIXTURE or MISSING and the fix for each.

Exit codes of gtm init: 0 done, 1 usage or file error, 2 instance or key problem, 3 refused key. It refuses a credential that can approve (a person's session), because a coding agent must only propose.

Put the key in your environment

Goal: Claude Code finds the key through GTMOS_AGENT_TOKEN and the key never lands in a file you might commit.

Windows PowerShell (persistent, then open a new terminal):

[Environment]::SetEnvironmentVariable('GTMOS_AGENT_TOKEN', '<agent key>', 'User')

macOS or Linux: add this line to ~/.zshrc or ~/.bashrc, then open a new terminal:

export GTMOS_AGENT_TOKEN='<agent key>'

The MCP address defaults to http://localhost:3004/mcp. To point at another address, set GTMOS_MCP_URL. .mcp.json reads it as ${GTMOS_MCP_URL:-http://localhost:3004/mcp}.

In a new terminal, echo $GTMOS_AGENT_TOKEN (or $env:GTMOS_AGENT_TOKEN on PowerShell) prints something that starts with gtm_. Do not paste that output anywhere.

Connect Claude Code

Goal: the gtmos MCP server shows as connected, with all nine tools.

  1. In Settings > Developer, the Connect Claude Code / Codex card creates the same key as gtm token create. Choose the coding agent, an agent name and the preset, then Create agent key. Copy the key now. The page also shows your org id, the MCP address and copy-ready snippets. Needs a human
  2. Set GTMOS_AGENT_TOKEN as above, then in the workspace folder run gtm init --url <api url> --key <agent key> --yes.
  3. Restart Claude Code in the folder and run /mcp.
/mcp lists gtmos as connected. Ask "What GTM OS tools do you have?" and Claude names gtm_describe, gtm_query, gtm_get, gtm_search, gtm_act, gtm_approvals, gtm_lineage, gtm_lineage_trace and search_records.

The .mcp.json that gtm init writes has this shape (the URL is your instance's MCP address):

{
  "mcpServers": {
    "gtmos": {
      "type": "http",
      "url": "${GTMOS_MCP_URL:-http://localhost:3004/mcp}",
      "headers": { "Authorization": "Bearer ${GTMOS_AGENT_TOKEN}" }
    }
  }
}

To make every MCP call in this project default to dev, run gtm init --env dev. It adds an x-gtmos-environment header to that entry. Without it, calls that name no environment run in prod.

Quick check that the key works, outside Claude (bash):

curl -s -X POST "http://localhost:3004/mcp" \
  -H "Authorization: Bearer $GTMOS_AGENT_TOKEN" \
  -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
A JSON answer that lists the nine tools. A 401 means the key is wrong, expired or revoked.

Keep the project current after you upgrade the CLI or the instance. Files you edited are kept:

gtm init --refresh --yes
Common errors
  • UNAUTHORIZED "No valid session or agent token": the variable is missing, wrong, revoked or expired (keys last 90 days by default). Create a new key, set it, restart.
  • "No commands match /setup-gtmos": Claude Code was already running when gtm init wrote the commands. Quit and start it again in that folder.
  • MCP tools fail after you restart or upgrade the stack: run /mcp to reconnect.
  • gtm init says the API is not reachable and shows an HTML-page hint: you passed the console address. Use the API address (default http://127.0.0.1:3001).
  • HTTP 403 on every call: the agent was killed, or the key belongs to another organization. A person revives the agent in Settings > Agents.
  • gtm init exits with code 3, "REFUSED": you gave it a person's credential. Use an agent key.

Connect Claude Desktop

Goal: ask questions of your instance from Claude Desktop. Know first what you give up.

Claude Code is the recommended way to build. gtm init, /setup-gtmos, the slash commands, the skills and the subagents are made for Claude Code and Codex. Claude Desktop gets the same nine tools, but none of that scaffolding. Use it to read, ask and review, not to build.

GTM OS speaks streamable HTTP and wants an Authorization: Bearer header. Claude Desktop starts local programs from its config file. To bridge the two you run a small helper in between. The steps below use mcp-remote.

Untested path. The bridge steps below were not run against a GTM OS instance, and the mcp-remote flags may differ in its current release. Whether a Claude Desktop custom connector (Settings > Connectors) can reach a GTM OS MCP server is not confirmed. If the bridge does not connect, use Claude Code.

  1. Create a key for it in Settings > Developer. Choose Other MCP client, give it its own name (for example claude-desktop-anna), and pick the read-only preset unless you need more. Use a short expiry. Needs a human
  2. In Claude Desktop open the Claude menu, then Settings, then Developer, then Edit Config. This opens claude_desktop_config.json. Its usual location is %APPDATA%\Claude\claude_desktop_config.json on Windows and ~/Library/Application Support/Claude/claude_desktop_config.json on macOS.
  3. Add the server. Node must be installed, because npx runs the bridge: 
    {
  "mcpServers": {
    "gtmos": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "http://127.0.0.1:3004/mcp", "--header", "Authorization:${GTMOS_AUTH}"],
      "env": { "GTMOS_AUTH": "Bearer <agent key>" }
    }
  }
}
  4. Quit Claude Desktop completely and start it again.
  5. In a new chat open the Add files, connectors, and more menu, then Connectors, and check that gtmos is listed.
The gtmos server appears with its tools. Ask "Call gtm_describe and tell me how many operations you can see." Claude answers with a number (671 in 0.2.5, fewer if your key cannot see some).

The cost of this setup: the agent key is written into the config file. Treat that file like a password. Never commit it, never share it, use a read-only or short-lived key, and revoke the key in Settings > Developer when you stop using Desktop. .mcp.json avoids this for Claude Code because it only references an environment variable.

If it does not show up
  • Check the JSON is valid and that you fully quit Desktop before reopening.
  • Read the logs: %APPDATA%\Claude\logs\mcp.log on Windows, ~/Library/Logs/Claude/mcp.log on macOS. A 401 means the key is wrong, expired or revoked.
  • Connection refused: the instance is not running, or you used another port. Check http://127.0.0.1:3004/health (it answers {"status":"ok", ...}).

The MCP toolbox in practice

Claude reaches all of GTM OS through nine tools. Eight are generic and cover every operation. One is a search tool for plain-language questions. Learn what each one does and you can read what Claude is doing.

The nine tools at a glance

Every call goes through the same path as the console and the REST API. Claude has no side door. Everything the console does is an operation, so what you can click, Claude can do, minus the things only a person may do (see What only a person can do).

gtm_describe: look before you call

Goal: get an operation's exact input shape so no field name is guessed.

Arguments: name (an operation name, optional) and class (Q, D, T, E or M, optional).

gtm_describe {}                                   the whole catalog
gtm_describe { "class": "E" }                     only customer-facing effects
gtm_describe { "name": "records.search" }         one operation in full

With no name you get one row per operation: name, class, method, summary, required scopes, error codes. With a name you also get the version, whether it is idempotent, whether it supports a dry run, and the input and output as JSON Schema.

For records.search: class Q, required objectType, optional filter and limit (1 to 50).

When a guide and the live answer from gtm_describe disagree, the live answer wins.

gtm_query: run a read

Arguments: name (required), input (an object, optional), environment (optional). It refuses write operations and tells Claude to use gtm_act.

gtm_query { "name": "agent.whoami" }
gtm_query { "name": "policy.get_dry_mode" }
gtm_query { "name": "instance.readiness", "input": { "status": "not_configured" } }
gtm_query { "name": "runtime.list_approvals", "input": { "state": "proposed", "limit": 20 } }
agent.whoami returns your organization id, the principal, how it signed in, the agent's name and version, the role, the effective scopes and canApprove (false for any agent). policy.get_dry_mode returns { "enabled": true } or false.

gtm_act: change something

Arguments: name (required), input, environment. It refuses read operations and tells Claude to use gtm_query.

gtm_act { "name": "score.score_account", "input": { "accountId": "<account id>" } }

score.score_account is a D operation. It runs now and writes a new qualification with its reasons.

gtm_act { "name": "outreach.send_message", "input": { "messageId": "<message id>" } }

outreach.send_message is an E operation. This call proposes the send. Nothing is sent. The result carries the approval, and a different person must approve and execute it. A send that has no lane fails with lane_required. While Dry Mode is on, E operations return drafts and create no approval at all.

For an E operation Claude reports "proposed", an approval id and who can approve. If Claude says "sent", that is wrong: ask it to read the approval back with gtm_approvals.

gtm_lineage_trace: where did this value come from

gtm_lineage_trace { "recordId": "<account id>", "objectType": "gtm.account", "property": "employee_count" }

For each property you get the winning value, the rule that chose it, a confidence, and the observations that fed it with their sources. A record with no provenance is labeled unverified, never invented. In 0.2.5, lineage for derived values and metrics is not filled in yet and comes back empty.

Which environment does a call use

gtm_query, gtm_get, gtm_search and gtm_act take an optional environment (dev, staging, prod or a named one). Chapter 5

Definitions as code

In GTM OS, your business logic is not hidden in settings screens. It is written down as definitions: small, versioned documents that the engines read at run time. You do not write them by hand. You tell Claude what you want, Claude writes the definition, and two different people make it live. This chapter shows every kind of definition, the change set that carries it, and the full life of one definition from your prompt to production.

What a definition is

Goal: know what you are asking Claude to write, and why nothing changes until a person signs it.

A definition has four parts:

PartMeaning
kindWhat sort of logic it is, for example definition.scoring_model or definition.lane.
keyIts name inside that kind. Engines look up fixed keys, such as default and icp_fit for scoring. Keep those keys stable.
specThe settings. The schema is strict: an unknown field is rejected, never ignored.
Environment and versionEvery save is a new version in one environment (dev, staging or prod). Old versions are kept.

Three rules hold for every definition:

  • Engines read only the signed version in the environment of the call. A draft or a proposed version is ignored. Where an engine ships a built-in default (scoring does), it runs that default until you sign your own.
  • The proposer never approves or signs. If Claude proposes it, a different human approves it and a different human signs it.
  • Production only accepts signed definitions that were promoted from a lower environment. You cannot write straight into prod.

The config store inside your instance is the source of truth. A git repository is an optional mirror, not a requirement (gtm mirror export writes the store out to a repo).

Ask Claude: "List every definition in dev and in prod and tell me which differ." It reads config.list for each environment and config.promotion_status.

The change set: how a definition travels

Goal: understand the four calls Claude makes to carry a definition from an idea to a draft in dev.

A ChangeSet is a bundle of one or more definitions (it can mix kinds). Over MCP, each one is an envelope:

The chain, from raw record to a reply

Goal: predict what a change in one engine does downstream.

  1. Data in. Import, CRM sync or a source mapping creates companies and contacts. These writes are marked bulk, so event plays and agent triggers skip them unless they opt in.
  2. Data Quality. identity_dq.normalize_records cleans domains, emails and casing. The duplicate scan proposes merges that follow your identity rule.
  3. Enrichment. Fills empty fields (employee count, industry, country, email, phone). Fit scoring reads employeeCount, countryCode and industry, so enrichment quality sets the ceiling for fit.
  4. Signals. Signals arrive from the daily scan, intent ingest, your own site and mailbox, or signals.record. The verification gate decides which ones count. Each new signal emits gtm.signal.observed.
  5. Score. Composite of fit (40 percent) and intent (60 percent) by default. A new qualification emits gtm.scores.computed.
  6. Handoff. When an account moves into qualified, the handoff routes an unowned account, creates a task and enrols a contact. The signal reaction can do the same on one strong signal.
  7. Outreach. The sequence cadence drafts the next step. A person approves it. The lane gate, the claims gate and the guardrails check it again at send time.
  8. Feedback. Replies are labelled. Unsubscribes, objections and hard bounces lower the account's intent score. Positive replies, meetings and won deals feed score.learn, which proposes new weights.

Goal: a scoring model that matches the client's ideal customer and buying signals, with a reason on every verdict.

What it does

KPIs it publishes

Events and ledger rows

  • Emits gtm.signal.observed for every new signal and gtm.signal.verification_changed on every verify, dispute, retract and restore. The account is re-scored on each.
  • A signal the gate held back is released once, when first verified. Its routing, enrolment, alert and plays run then.
  • The scan records its runs as the monitor score.signal_scan.

Dry Mode and guardrails

  • Signals has no engine mode. Recording a signal is an internal write and works in Dry Mode.
  • The scan spends real looot credits, so Scan for signals now is disabled, and nothing is queued, while the organization-wide Dry Mode is on or while signals.scan.enabled is false. The page says which one applies.
  • The scan stops at perRunCapUsd through the broker's ledger (never above 1 USD on demand).
  • Retracting never deletes. Turning the gate off does not replay held signals. They release when someone verifies them.

  • First-party signals. Send your product events, form fills and bookings in through the connectors or signals.record with partyTier: "first". Third-party sources: set partyTier to third.
  • Source mapping. Map any connected app's rows to signals with the source mapping flow (chapter 10), for example demo requests from a form tool.
  • New kinds. A new kind scores defaultWeight in this engine. Give it a rule here, and in the Score intent model if it should move the account score.
  • Evidence. Add evidence {sourceUrl, matchedText, confidence, provider} so a reviewer can decide fast.

The lifecycle

  1. mission.start creates it in intake. It does not execute.
  2. mission.clarify records questions and answers. An optional ask opens a numbered open ask for a person. Answering it feeds the answer back.
  3. mission.plan records the plan. mission.submit_for_approval proposes it.

  7. mission.cancel stops it from any non-terminal state. mission.get and mission.list read it.

The control stack, in order

Goal: know every check an action passes, so you can say why something was allowed, drafted, held or refused.

Every operation takes the same path, whether it comes from the console, the CLI, the API or Claude over MCP. There is no side door. For a customer-facing effect (an email, an ad budget change, a page publish, a CRM write, a merge), these checks apply in this order:

#CheckWhat it can doSet by
1Who is callingRefuse. Roles, key scopes, the human behind the agent. Some operations are human-only.Roles and keys
2The gate policyDecide: allow, require_approval, draft or deny. With no policy, an effect needs approval.Gate policy
3The autonomy capTurn an allow back into require_approval when the autonomy level is below A3.Autonomy ladder
4Dry Mode and the engine's modeTurn the action into a draft. Nothing runs, no approval is created.Dry Mode
5Guardrails and the net-new ruleHold an action (quiet hours, a reached cap), or force a human approval.Guardrails
6The approval and four-eyesA different human approves, then a human executes.Approvals

The autonomy ladder

Goal: understand what "autonomy" really means in GTM OS, what you can set, and what stays fixed. The product uses the words "the autonomy ladder", with five levels.

LevelNameMeaning in the code
A0ObserveRead and answer questions.
A1SuggestProduce drafts and recommendations as records. No operations beyond reads.
A2ProposePropose operations. Every effect needs approval. This is the default.
A3Act within policyEffects may be auto-approved by a policy, within caps. Exceptions escalate.
A4Mission autonomyRun a human-approved plan under an envelope, replan inside it, escalate outside it.

What the ladder really does

  • It applies to effects only. Reads, data writes and stage transitions are not affected.
  • The disposition check tells only two groups apart: below A3 (A0 to A2) and A3 and above (A3 and A4). Below A3, an effect that a rule would allow becomes require_approval. At A3 or above it may stay allow, but only if no human approvals are required for that scope.
  • Raising the level does not by itself turn on automation. Without a gate policy or an envelope that approves the action, an effect still needs a person, because the default for an effect is require_approval. The level only removes one brake. To run without a person, a gate rule or an envelope must allow the action, and every other check in the control stack must pass too.
  • A first message to a net-new contact is never auto-sent. It always waits for a human approval, at every autonomy level, envelope and policy. This is a fixed rule, not a setting.

How a person sets it

policy.set_autonomy_scope is human-only. A scope is org (the organization default and ceiling), engine:<key> (one engine), or a narrower scope such as campaign:<id>, play:<key> or lane:<lane>. Each scope can set three things:

FieldMeaningRule
maxAutonomyLevel (0 to 4)The ceiling.A narrower scope can only lower it, never raise it.
requiredApprovalsThe minimum number of human approvals.A narrower scope can only require more.
autonomyLevel (0 to 4)The level actually granted.The narrowest scope that sets it wins. Never above the ceiling. Default A2.
  • A narrower scope may grant more than a broader one (that is the point of per-campaign autonomy), but never more than the ceiling. A write that would loosen a ceiling or an approval minimum is refused with FORBIDDEN.
  • The outreach engine is guarded: its engine grant can never be higher than the organization's grant, even if you set it higher. Lower the org grant later and outreach drops with it.
  • The cap applies only once the organization has at least one autonomy scope on record. With none, the check does nothing and every effect keeps the default approval path.
  • The engines you can scope are the ones in the engine list below.

The easy way: the setup wizard's Autonomy per engine card (Setup, Rules). It offers A1 suggest, A2 approve each, and A3 act within caps, and sets each engine dry or live. Gate policy and envelopes

Goal: for the rare case where you want an action to run without a person, know the two tools and their limits. Both are human-only and are not signed or promoted like definitions.

Gate policy

A gate policy is a table of rules. Each rule has a match (facts such as class, op, principalKind, plus facts an operation adds), a disposition (allow, require_approval, draft, deny), and optionally approvers, approvedBy (policy or envelope), quorum, expires and forbidPrincipalKinds. A rule that forbids agent turns an agent's attempt into deny. If no rule matches, the default applies: reads, data writes and stage transitions are allowed, and effects need approval. Set it with policy.set_gate_policy (each save is a new version, old versions are kept), read it with policy.get_gate_policy, and test it with policy.evaluate. Needs a human No console screen or CLI command exists for it in 0.2.5. A person calls the operation with their own session.

Envelopes

An envelope is a scoped, budgeted, time-bound pre-approval. envelope.grant (human-only) takes the grantee (granteeKind, granteeRef), the operations it covers as name patterns (for example enrich.*), an optional budgetEur, the window (windowFrom, windowTo) and whether it is revocable. envelope.revoke ends it at once. envelope.get and envelope.list_for_grantee read them. Activating a lane (lane.activate) grants that lane's spend envelope through the approval gate, sized by envelopeBudgetEur over windowDays.

  • An envelope's constraints field is stored but not enforced in 0.2.5. Do not rely on it.
  • A rule with approvedBy: envelope uses an envelope. A rule with approvedBy: policy approves on the policy's own authority.
  • The claims policy in route_to_approver mode, and the net-new rule, override any auto-approval.
Out of the box, every effect needs a person. This chapter describes the mechanism. It does not recommend turning automation on. If you do, start with one engine, one lane, a small budget and a short window, and watch Actions and Operate > Cost.

Not confirmed: in 0.2.5 the source shows no console screen and no CLI command for policy.set_gate_policy. A person would call the operation over REST with their own session token. No tested, worked example of an auto-approved send exists, so this chapter describes the mechanism only.

Keep your instance healthy, reachable, backed up and current. An upgrade never touches, removes or loses your data. Every command here is copy and paste, and each one says what you should see.

Run commands from the instance folder: the folder that holds docker-compose.yml and .env (for example ./instance after /setup-gtmos). Or add --dir <path> to a gtm command.

Check that it is healthy

Goal: a two-minute check you can run any time, or ask Claude to run.

The MCP server also answers /ready. It checks the database and migrations, and returns 200 when ready and 503 when not.

Ports are local only by default

Goal: know who can reach the instance, and open it on purpose when you need to.

Changed in 0.2.5. The console (3000), API (3001) and MCP (3004) ports bind to 127.0.0.1 by default, like Postgres. An older instance becomes local-only on its next gtm up or gtm upgrade. If you only use GTM OS on one machine, nothing changes for you.
GTMOS_BIND_ADDRESS in .envMeaning
127.0.0.1 (default)Reachable from this machine only. Use it with a reverse proxy on the same machine.
0.0.0.0Reachable on every network interface. Only behind a firewall that allows exactly the ports you intend.
A private IP such as 10.0.0.5Reachable on that interface only, for a proxy on another host in the same private network.

To change it, edit GTMOS_BIND_ADDRESS in .env and run gtm up again, or create the instance with gtm up --bind 0.0.0.0. A --bind flag passed to an existing instance is ignored and reported, because the existing .env wins. gtm up prints the effective address and warns when it is 0.0.0.0.

Coming from an older instance? The first gtm up or gtm upgrade on 0.2.5 warns when .env has no GTMOS_BIND_ADDRESS, then writes 127.0.0.1 into it. If a teammate, a webhook or an MCP client on another machine reached the instance by IP address, use a reverse proxy or 0.0.0.0.

Goal: people reach GTM OS at https://app.acme.example while the instance stays closed to everything except your proxy.

Common errors
  • Login redirects loop or cookies are not stored: the public addresses in .env do not match what the browser uses, for example http:// in .env and https:// in the browser.
  • Nothing answers by IP address after an upgrade: the ports are local-only now. See the previous section.
  • Claude gets 401 from the public MCP address: the key is wrong or expired, or the proxy strips the Authorization header.

Back up

Goal: a copy of your database you can restore from, and your master key kept apart from it.

The backup every upgrade takes

Every gtm upgrade stops the API, worker, MCP server and console, then writes a full backup of the database (every organization in it) as backups/gtmos-pre-upgrade-<stamp>.dump. It reads the file back to prove it is readable. It also keeps .env.pre-upgrade-<stamp> and docker-compose.yml.pre-upgrade-<stamp> next to it. The newest five are kept. The backup is never restored automatically.

Take your own backup

There is no gtm backup command in 0.2.5. Use the same pg_dump the upgrade uses, run inside the Postgres container. Run it in a bash or zsh shell. In Windows PowerShell the > redirect corrupts a binary file.

mkdir -p backups
docker compose --env-file .env -f docker-compose.yml exec -T postgres pg_dump -U gtmos -d gtmos -Fc --no-password > backups/gtmos-manual.dump
A backups/gtmos-manual.dump file larger than zero bytes. Check it is readable with docker compose --env-file .env -f docker-compose.yml exec -T postgres pg_restore --list < backups/gtmos-manual.dump, which prints the contents list.

On Windows PowerShell, write the file inside the container and copy it out instead:

docker compose --env-file .env -f docker-compose.yml exec -T postgres pg_dump -U gtmos -d gtmos -Fc --no-password -f /tmp/gtmos-manual.dump
docker compose --env-file .env -f docker-compose.yml cp postgres:/tmp/gtmos-manual.dump ./backups/gtmos-manual.dump

Untested: the PowerShell variant was not run and is not in any product doc.

Keep the master key apart

A dump does not contain GTMOS_MASTER_KEY. Every stored credential (connections, OAuth tokens, SSO secrets) is sealed with that key, so a restored database without it cannot read them. Copy the key from .env into a password manager when you install, and again if you ever change it. Keep it somewhere other than next to the dumps. The dump itself is not encrypted and contains personal data, so protect the folder it lives in.

Export one organization

gtm org export --org <orgId> --out ./acme-export --format parquet --dry-run
gtm org export --org <orgId> --out ./acme-export --format parquet
  • It writes a portable bundle for one organization: one Parquet file per table (default), or with --format sql one file of INSERT statements. A manifest lists each table with its row count.
  • With --env <env> and GTMOS_API_URL set, it also writes that environment's configuration (your definitions and settings).
  • It connects as the restricted application database role (DATABASE_URL or --database-url), so it can read only that organization's rows. It only reads. --dry-run prints the plan and writes nothing.
The dry run lists the files it would write. The real run leaves a folder with one file per table and a manifest.

gtm org export needs DATABASE_URL set to the restricted application role (gtmos_app). Check your .env for the value.

Update to a newer release

Goal: move your instance to a newer release without losing anything. Every release only adds (new tables, nullable or defaulted columns, indexes). The updater refuses any release that does not, and there is no override.

Which version am I on?

The CLI version and the instance version are separate. gtm upgrade --check shows both, plus what the signed release list offers, and changes nothing. Releases before 0.2.5 published images only as 0.2.2 and stable. CLI versions 0.2.3 and 0.2.4 shipped no images, so an instance installed with either still runs the 0.2.2 images.

  1. Upgrade the CLI first. It renders the compose file your instance runs on, so it must be at least as new as the release you move to. If it is too old, gtm upgrade stops and says which version to install. 
    npm i -g @gtmos/cli@latest
  2. See what is available: 
    gtm upgrade --check
  3. Rehearse. It prints every command and changes nothing: 
    gtm upgrade --channel stable --dry-run
  4. Upgrade. --yes is required because it migrates your live database: 
    gtm upgrade --channel stable --yes
  5. In Claude Code, run /mcp to reconnect. Then, in each project folder, take the newest skills and subagents (files you edited are kept): 
    gtm init --refresh
The last line of the upgrade reads UPGRADE OK. A plain gtm upgrade on a pinned install ends with RE-VERIFIED <version>, NOT UPGRADED instead.
A plain gtm upgrade never moves a pinned install. With neither --channel nor --to, it only re-pulls and re-verifies the release you already run. To move, name the target: --channel stable, or --to <version> for an exact release.

What the upgrade does, in order

  1. Fetches the signed release list and checks its signature. It plans the path by the list's rules: no downgrade, no skipped required stop, additive-only releases, a minimum CLI version. Any failed check refuses the upgrade before anything is pulled.
  2. Preflight. Only one update at a time. Free disk must be at least twice the database size plus 2 GB.
  3. Pulls the new images. Each image's digest must match the signed digest.
  4. The additive-only guard reads every pending migration and refuses anything that drops, renames, retypes, deletes or overwrites.
  5. Stops the API, worker, MCP and console gracefully, and takes a backup that it reads back to verify.
  6. Rehearses on a scratch copy: it restores that backup into a scratch database, migrates it and compares it with your live data (tables, columns, types, row counts, row checksums). Any difference refuses the upgrade.
  7. Pins the version in .env, runs the migration inside the new image, starts the services, and verifies health and schema.

What is preserved

  • All your data: records, history, definitions, approvals, connections and keys.
  • Your apps and configuration. An upgrade changes no installed engine app. An owner or admin proposes an app update in Settings > Packages, a second person approves it, and your own edits are merged in.
  • Your GTMOS_MASTER_KEY. Keep your own copy.

Moving to 0.2.5 from 0.2.2, or from CLI 0.2.3 or 0.2.4 on 0.2.2 images

  • Upgrade the CLI first. This is not optional.
  • Name the target. An install set up with --version 0.2.2 is pinned: run gtm upgrade --channel stable --dry-run, then gtm upgrade --channel stable --yes.
  • Ports become local-only. See Ports are local only by default.
  • Read the settings table: GTMOS_LIVE, instance keys, who can import CSVs.
  • Account scores can move once on the first rescan. Preview it before it runs: ask Claude to run score.rescan_preview, which writes nothing.
  • Run gtm init --refresh in each project folder.
  • Already on a newer 0.2.x? The path is the same. If a release in between is a required stop, gtm upgrade adds it as an extra hop and takes a backup at each hop.

Check it worked

  1. gtm doctor shows the sources you expect as live.
  2. The two health calls from Check that it is healthy report the new version.
  3. The upgrade said verification passed, and a snapshot is in backups/.
  4. Row counts of your main tables match what you noted before.
  5. Dry Mode send check: propose one send to an internal address and confirm that a different person has to approve it.
  6. .claude/agents in each project holds the role subagents after gtm init --refresh.

Roll back

Goal: get the previous release back. You almost never need a database restore.

When an upgrade fails

It rolls back by swapping the images back. The previous compose and .env files and the previous images are restored, and the services restart on them. The database is never restored, dropped or recreated by an upgrade. The verified backup stays in backups/. This works because every migration only adds things, so the previous code runs on the migrated database.

Run gtm upgrade --check and the two health calls. They tell you which release is running.

Go back after a successful upgrade

Use the oldest stamp from that upgrade run (one upgrade may take several hops). From the instance folder:

docker compose --env-file .env -f docker-compose.yml stop api worker mcp console
cp .env.pre-upgrade-<stamp> .env
cp docker-compose.yml.pre-upgrade-<stamp> docker-compose.yml
docker compose --env-file .env -f docker-compose.yml up -d
gtm upgrade --check

Use docker compose here, not gtm up. gtm up writes the compose file again from the installed CLI and replaces the copy you just restored. The previous images must still be in your local cache or on the registry, and a pulled image must match its signed digest, so do not remove old images until you are sure.

gtm upgrade --check names the previous release as the one your instance runs.

Restore a backup (last resort)

Only if something other than an upgrade damaged your data. Never restore over the live database. Keep the current one by renaming it, then restore into a new one. gtm upgrade --help prints the exact commands. In short:

  1. Stop the services and rename the live database so nothing is lost: 
    docker compose --env-file .env -f docker-compose.yml stop api worker mcp console
docker compose --env-file .env -f docker-compose.yml exec -T postgres psql -U gtmos -d postgres \
  -c "ALTER DATABASE gtmos RENAME TO gtmos_before_restore_<stamp>"
docker compose --env-file .env -f docker-compose.yml exec -T postgres createdb -U gtmos -O gtmos gtmos
  2. Restore in three sections, with one repair between the first two (a function that a 0.2.2 check constraint calls needs its search path set). Use the dump you chose: 
    docker compose --env-file .env -f docker-compose.yml exec -T postgres pg_restore -U gtmos -d gtmos --section=pre-data < backups/gtmos-pre-upgrade-<stamp>.dump
docker compose --env-file .env -f docker-compose.yml exec -T postgres psql -U gtmos -d gtmos \
  -c "ALTER FUNCTION public.is_valid_record_link_object_type(uuid, text) SET search_path = public"
docker compose --env-file .env -f docker-compose.yml exec -T postgres pg_restore -U gtmos -d gtmos --section=data < backups/gtmos-pre-upgrade-<stamp>.dump
docker compose --env-file .env -f docker-compose.yml exec -T postgres pg_restore -U gtmos -d gtmos --section=post-data < backups/gtmos-pre-upgrade-<stamp>.dump
  3. Put .env and docker-compose.yml back from their .pre-upgrade-<stamp> copies, then docker compose --env-file .env -f docker-compose.yml up -d. The renamed gtmos_before_restore_<stamp> database stays until you drop it yourself.

Restoring a dump also needs the original GTMOS_MASTER_KEY, or the stored credentials cannot be read.

Verify a release yourself

  • Releases are announced in a signed list, releases.json, with an ed25519 signature next to it. The CLI trusts only the release keys built into it. The default address is https://ay-automate.github.io/gtmos-releases/releases.json, and GTMOS_RELEASE_MANIFEST_URL overrides it. An air-gapped site serves a mirrored list that is still signed.
  • For each release the list gives the version, date and channel, whether it is a security release, the minimum CLI version, the oldest version it can be reached from, any required stops, whether it is additive-only, and the sha-256 digest of the api, worker, mcp and console images.
  • gtm upgrade --check fetches and verifies the list and prints what it offers. It changes nothing. Before an upgrade changes anything the CLI also checks that the images come from an allowed registry (ghcr.io/ay-automate unless you mirror), and after the pull that every digest equals the signed one.

Glossary

Agent key
The credential Claude uses (GTMOS_AGENT_TOKEN). It acts as the agent, proposes, and can never approve.
Approval
A proposed action waiting for a person other than the proposer. Proposals expire after 7 days.
Autonomy ladder
Five levels, A0 Observe to A4 Mission autonomy. The default is A2 Propose. It only removes one brake. It does not turn automation on by itself.
Binding
How a capability is acquired: backend (looot, Composio, MCP or native), the provider operation, a price cap, verification and fallbacks.
Blueprint
A ready-made set of definitions for a go-to-market motion. Ten ship in 0.2.5. Apply one in dev as a proposal, then customize.
Canon
The built-in set of object types (accounts, contacts, deals and others) and the rules for editing them.
ChangeSet
A bundle of definition changes proposed together, validated, approved by a different person, then published.
Claims gate
A check that a stat, result or named customer in outbound copy is backed by active proof.
Composio
The way GTM OS connects to your own apps (CRM, Slack, Search Console). looot is for outside data.
Definition
A signed, versioned piece of business logic. The engines read the signed version in the call's environment.
Dry Mode
While on, an effect becomes a draft and nothing leaves the system. There is an organization master and one mode per engine. The stricter wins.
Effect (E)
An operation that touches a customer or an outside system. It is proposed, never run directly.
Engine
One of seven packaged workers: Score, Outreach, Performance Ads, SEO & GEO, Data Quality, Enrichment, Signals.
Envelope
A scoped, budgeted, time-bound pre-approval that a person grants. It can approve matching operations without asking each time.
Environment
dev, staging or prod. Config lands in dev. Only signed definitions reach prod.
Four-eyes
The person who proposes can never approve, sign or execute. A second person is needed from day one.
Guardrails
Organization-wide caps and the send window. A reached cap holds an action. It runs later.
Human-only
An operation that refuses an agent key. A person must do it in the console or the CLI.
Lane
A sending channel with its limits (daily cap, touch window, deliverability checks, envelope budget). Every send needs an active lane.
Ledger
The audit trail of engine actions (Operate > Actions).
Lineage
The receipts behind a value: which source, which rule.
looot
The data-acquisition layer for enrichment, emails, lists and intent.
MCP
Model Context Protocol. How Claude talks to GTM OS.
Mission
A bounded, approved plan that an agent steps through under limits on steps, cost and time.
Net-new rule

Operation
One named capability on one surface (REST, SDK, CLI, MCP). 671 in 0.2.5, in five classes.
Package
A signed bundle that adds apps, definitions, agents or engines. Installing and enabling are proposals.
Play
An automation: a trigger, a filter, and steps that call operations.
Promote
Move signed config from one environment to the next. A different person approves.
Proof library
The approved evidence behind claims, in Settings > Proof library.
Sequence
An ordered set of email or LinkedIn steps with waits, variants and exit rules.
Sign
A person other than the proposer marks a definition version as the one engines may use.
Skill
A bounded authority grant (operations, cost ceiling) an agent activates one at a time. Also a Claude Code skill in your workspace.
Trust key
The name of an engine in the approval and mode system, for example outreach or crm_writeback.
