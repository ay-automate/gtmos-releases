Release notes

GTM OS 0.3.0

CLI: @gtmos/cli 0.3.0. Images: ghcr.io/ay-automate/gtmos-{api,worker,mcp,console}:0.3.0 (also tagged stable), plus pgvector/pgvector:pg16.

0.3.0 is the Integration Bridge. You link your integrations account once with a project key, then connect any of about 1,700 apps from GTM OS, with as many accounts per app as you need. Every read says whether it returned data, nothing, an answer it did not recognise, or a failure. Reads and writes in apps are metered and capped, and writes go through the same approvals as everything else. On top of it come ready-made mapping packs, shipped recipes for SEO, GEO, ads and CRM data, privacy rules for a person's own mail, calendar and files, motions your organization owns, and a console layout you can set yourself. It follows release 0.2.6.

The catalog is now 900 operations (406 Q, 334 D, 5 T, 33 E, 122 M) and 47 definition kinds.

Product rules that hold for everything below: nothing sends, writes to a CRM, spends money, merges or publishes without approval. Agents propose and never approve their own work. Dry Mode holds everywhere. Numbers are real, or they are a dash with a reason.

Before you rely on it

  • Live checks against real app accounts were not run for this release. Everything was tested against simulated providers and synthetic answers. So the new mapping packs and recipe templates ship as beta: their tool names, arguments and answer shapes come from the vendors' documentation and a catalogue sample, and are not verified against the live services. A wrong guess fails loudly (the install is refused, or the read is "unrecognised"); it never writes guessed data. Treat a pack or recipe as tested only after you have run it against a real account.
  • There is no Composio sign-in in GTM OS. You link the integrations account with a project API key only (the key that starts with ak_), pasted in Integrations > Apps or set as COMPOSIO_API_KEY. A Connect key (ck_) is refused. Pasting the key is the first step, not the whole setup: see "Connect your apps" below.
  • Source mappings signed before 2026-11-17 (UTC). A source mapping signed before the start of 2026-11-17 UTC that sends its own query text (SQL, JQL and the like), or that reads a person's own app without naming whose account it reads, keeps running as before, with a warning on every run. One signed on or after 2026-11-17 is refused until it is published again the new way: through the shipped pack, or with an account pin (and the confirmation of who in the organization may see the data).
  • Install and upgrade go through the gtm CLI and the published images only. Install with gtm setup or gtm up, upgrade with gtm upgrade; both use the images on ghcr.io/ay-automate. There is no other install path.
  • Snowflake is held. Its pack ships but cannot be installed: the app's query tool can also change data. The six packs added in this version (Gong and Calendly with their own-user lookup, BigQuery, ClickHouse, Leadfeeder, Webflow) are beta.

Connect your apps

Link the integrations account once. An owner or admin opens Integrations > Apps and pastes the project key (ak_...). GTM OS tests it, stores it sealed and starts loading the app list: the first apps appear within seconds and the full list (about 1,700 apps) within minutes. To get the key, open the Composio dashboard, select Platform, your project, Settings, the API Keys tab, then Create API Key with these permission areas: Toolkits (Read), Tools (Read), Tool execution (Read and write), Auth configs (Read and write), Connected accounts (Read and write), Triggers (Read and write), Webhooks (Read and write), Observability (Read).

What else you do once.

  1. Callback verifier. Copy the address from the Apps banner (your console address followed by /integrations/callback) and set it as the callback verifier in your integrations project. GTM OS cannot set or see that setting, so the banner always says "Not verified". Apps that sign in need it.
  2. The worker must run. The app list loads in the worker. Without it the list stays empty.
  3. Set the integrations engine live. Writes become real approvals only after the integrations engine mode is live (policy.engine_modes.set). Until then a proposal reads "Drafted, nothing was done".
  4. Two kinds of sign-in. Apps that use OAuth pass through a hosted link page and the app's own consent page. Apps that use an API key stay inside GTM OS.
  5. Credits. Accounts that use the managed sign-in need credits on your integrations plan.
  6. Several organizations on one installation. The app list and app actions are shared and load only through the installation key (COMPOSIO_API_KEY on the api and the worker). An organization with its own key connects and runs with it, but cannot load the shared list.
  7. Webhooks need a public https address. Set GTMOS_PUBLIC_API_URL, then run integrations.webhook.subscribe.

Connect apps, as many accounts as you need. Click an app in the grid, then Connect. GTM OS checks who the account is, warns when the same login is already connected, and makes one safe read before it says Connected. Any number of accounts per app; every row records the account it came from. When accounts disagree, priority wins, then recency, and both values are kept. A member may add a personal account, shared in the organization only after the owner confirms. A CRM can read one account or merge all of them, and writes back to none, the primary or the origin account. A member who leaves has their personal accounts paused.

Truthful status. Every read is data, empty, unrecognised or failed. A sync is "Succeeded" only when rows came back; an empty answer is "Succeeded, read nothing". A changed answer shape is reported and nothing is mirrored. Each read leaves a receipt, and a drop to zero rows alerts the owner.

Reads and writes in apps. integrations.read runs read tools. integrations.act proposes writes (tier T2) and integrations.act_destructive proposes deletes and unclassified tools (tier T3); a different person approves. Every call is metered (about $0.0003) on the cost ledger and counts against a monthly limit an owner or admin sets. A warning goes out at 80%. Essential work (approved sends, a person's own setup steps and syncs, compliance withdrawals, and reading replies, bounces and stop requests) keeps running past the limit up to 1.5 times it, and never less than $1.00 a month. Owners and admins can set a tool's class, turn it off or limit its roles. A lighter route and autonomy for a short list of reversible internal writes is off by default, until an owner or admin signs a policy with caps and a kill switch.

Needs, recipes and provider policy. Nineteen needs (search analytics, AI answers, web analytics, CRM records, ads performance and more). A signed recipe says which read tool of which app serves a need; a signed provider policy says how providers combine. A person signs every recipe and policy; an agent can only propose. A need that is not served reads not_connected, never a guess.

Your own OAuth app. An owner or admin can connect the organization's own OAuth app for Google, Microsoft, HubSpot, Salesforce, Slack, LinkedIn and Meta apps, so people sign in through your own consent screen. The client secret is sealed and never shown again.

Outside agents. Claude Code, Codex and any MCP client get per-key grants: which apps, which tools, which account, calls per minute and an end date. Everything else under integrations.* is closed to agent keys. An agent calling apps with an agent key has a default limit of $1.50 per rolling 24 hours. Two built-in agents (seo-analyst, provider-policy-manager) read needs and propose provider policy, and every figure they give carries its need, provider, account and read time. Perplexity and your own OpenAI-compatible endpoint are new model connections.

What else is new

  • Who can approve. One setting per workspace: "A second person must approve" (the default, kept for existing workspaces) or "I can approve my own changes" for an owner or admin signed in as themselves. Agents, API keys and automations can never approve, sign or run anything for themselves. Change it in Settings > Safety.
  • Mapping packs (beta). 43 ready-made source mapping packs, installed with integrations.pack.install. A pack that reads one person's account needs an account pin and a consent. integrations.pack.generate builds a mapping from a real sample.
  • Six more packs (beta). BigQuery and ClickHouse accounts from a view you create, Calendly bookings, Gong calls, Leadfeeder visits and Webflow form submissions. Calendly and Gong read only the installer's own data.
  • Jira (beta). Reads issues of one project through a bound search. Nobody writes their own search words: an agent, an API key or a flow cannot send its own JQL.
  • Airtable columns. You pick the table and columns at install. Before every sync the confirmed columns are checked again; a removed, renamed or retyped column stops the read and names it.
  • Free-mail domains. An address at a common free-mail provider is no longer a company domain anywhere a source mapping fills one: it does not create, match or merge an account.
  • Person-account apps. Apps that hold one person's own data need an account pin on every mapping, and only a person signed in can preview or pin them. Added: Google Drive, Google Docs, Google Meet, Microsoft Teams, Discord, Google Sheets, Google Slides, OneDrive, Dropbox, Box, Excel, SharePoint, Google Tasks and Jira.
  • Adapter samples. Sample rows from an adapter session are shown only to a person signed in. Agents, API keys and automations get the same shape with no values.
  • Shared call budget. One hourly budget of app calls per organization and per app, shared by background syncs and GEO recipe reads. A run that meets it stops, keeps what it read, and continues on its next scheduled run.
  • Xero (beta). The contacts pack reads only customers changed since the last run.
  • Warehouse reads. A read can wait for a query that is still running (at most five minutes a run) and never sends the query twice.
  • Calendar and mail privacy. A meeting marked private or confidential is not copied in. A meeting or e-mail that becomes private later, or an e-mail moved to spam or Junk Email, is hidden ("(private event)", "(private message)") and listed in the privacy erasure audit.
  • Preview through an account. A person can preview a connected app, or start an adapter, through a chosen account. Agents and API keys cannot choose one.
  • SEO and GEO recipes (beta). Templates for Semrush and Ahrefs backlinks and Peec AI answers. A person proposes one and a different person signs it. Search Console stays required for SEO and GEO, and can be served by three signed recipes on your own account. Ahrefs now runs on your own account and shows top rows, not account totals. GEO can take answers from a connected AI visibility app, provider history can be imported after you confirm the calls and cost, and seo_geo.get_visibility says which AI engines are covered.
  • GEO vendors. Profound, Otterly.AI and Scrunch AI as GEO answer sources with your own key.
  • Ads and CRM needs (beta). Recipe templates for Google Ads, Meta Ads and LinkedIn Ads performance, and for HubSpot, Salesforce, Pipedrive, Attio and Zoho records. Performance Ads reads through them when no native connection exists.
  • Needs follow-ups. An organization with no deals, records or ad spend reads as empty with a warning instead of failing; one odd row no longer makes a whole answer unrecognised; ad spend is booked in the account currency.
  • Workspace layout. Show or hide sidebar sections, pages, engine tabs and apps for everyone (owner or admin) or just for you. Hidden is not blocked. An accent colour, a logo, light or dark, and a compact density.
  • Engine manifests. The installed copies of five first-party engine manifests are refreshed, so engine work they blocked before now runs.
  • Motions. A motion is now an object your organization owns, with versions a different person approves, offers, rules of engagement between motions (precedence, one weekly touch cap per company, inbound signals that pause outbound), a budget and per-motion measuring.
  • Templates and setup. A plain blueprint apply no longer overwrites what the organization already has: a different definition is kept and the template's copy is added next to it. In setup, "What should we never do?" becomes proposed suppression rules, unanswered weekly hours draft conservative send caps (25 e-mails a day, 10 new accounts a week), "Re-draft with site facts" never overwrites an edited or approved card, and the sender postal address is a field on the consent card.
  • Search. Signed persona, segment, play and scoring-model definitions are searchable, without contact details.
  • Approvals. A proposal past its 7-day deadline reads as expired everywhere, and closed approvals can be archived.
  • Agent scope. An agent passes an owner or admin check only when its own scope also holds the permission.
  • Paused lane. An approved action in a paused lane is refused with POLICY_DENIED.
  • Business calendar. definition.business_calendar: working days, holidays, blackouts and the fiscal year. Nothing changes until one is signed.
  • Buying triggers. definition.buying_trigger, and signals now age from when the event happened.
  • Markets. Each recipient gets the privacy rules, send window and language of their market.
  • GEO setup. AI visibility setup in the wizard, and several brands per organization.
  • Positioning and exclusivity. One competitor list, definition.positioning, client exclusivity for agencies, proof in setup, and a funnel baseline.
  • Code quality. Several fixes that matter for the upgrade: the unsubscribe secret, duplicate detection and rate limits.

Settings you must know

  • COMPOSIO_API_KEY on the api and the worker: the installation key. On an installation with several organizations the app list and app actions load only through it. The worker must run for the app list to load.
  • PUBLIC_CONSOLE_URL on the api: without it a connect has no page to come back to. GTMOS_PUBLIC_API_URL must be a public https address before integrations.webhook.subscribe.
  • The monthly limit for app calls is set in Integrations > Apps or with integrations.usage.set_cap (owner or admin). An agent calling apps with an agent key has a default limit of $1.50 per rolling 24 hours (GTMOS_INTEGRATIONS_AGENT_DAILY_CAP_USD; 0 blocks those calls).
  • Each connected account has a call rate limit: a burst of 60, then one call per second (GTMOS_INTEGRATIONS_ACCOUNT_RATE_BURST, GTMOS_INTEGRATIONS_ACCOUNT_RATE_PER_SECOND), counted per server process.
  • The shared hourly call budget of background runs. The window is the clock hour (UTC). These are operator settings (environment, whole numbers); an invalid value is logged and the default applies:
    • calls per organization per hour, every app and every background run: 3000 (GTMOS_INTEGRATIONS_JOB_CALLS_PER_HOUR, 1 to 1000000);
    • calls per app per organization per hour: 1500 (GTMOS_INTEGRATIONS_JOB_CALLS_PER_APP_PER_HOUR, 1 to 1000000);
    • calls every run may make whatever the window holds: 3 (GTMOS_INTEGRATIONS_JOB_CALLS_MIN_PER_RUN, 0 to 1000000; 0 makes the ceilings strict).

    A run's fair share is half of what is left of the tighter ceiling when it first asks. Calls a person makes, and a sync or visibility run a person starts, are counted in the window but never stopped by it.

  • Trashed e-mail stays in GTM OS by default. To hide an e-mail moved to the trash or Deleted Items too, an owner or admin sets mailbox/redact_trashed to true with connections.set_provider_setting (MCP or CLI; no console field yet). Spam and Junk Email are always hidden.
  • GTMOS_CUSTOM_MODEL_PRIVATE on the api and worker: an owner's own model endpoint on a private address is refused by default once the installation holds more than one organization (on allows it, off refuses it).
  • GTMOS_AHREFS_SHARED_ACCOUNT_GRACE=true keeps Ahrefs on a shared account for one release. Without it, Ahrefs needs the organization's own account.
  • In production, UNSUBSCRIBE_TOKEN_SECRET set to the public default value is refused for contact unsubscribe links too. Set a real secret before you upgrade.
  • The signals.decay flag is on by default: signals age from when the event happened, so scores of accounts whose signals describe old events go down at the next rescore. To keep the old behaviour, set flags.set { key: "signals.decay", value: { eventTime: false, maxAge: false } }.
  • Existing workspaces keep "A second person must approve". Owners and admins change it in Settings > Safety.

Upgrade

An upgrade never touches, removes or loses your data. Every migration only adds, the updater takes a verified backup first, and a failed upgrade rolls back by swapping the images.

0.3.0 is reached from 0.2.6 only. A 0.2.5 instance goes 0.2.5, then 0.2.6, then 0.3.0, and gtm upgrade plans those steps. 0.3.0 needs @gtmos/cli 0.3.0 or newer: the 0.3.0 compose file and the rollback check come with it.

Before you upgrade:

  1. Find the agent-key automations that will stop. From 0.3.0 an outside agent key may not run any composio.* operation, any integrations.* operation beyond the reads that name no app and the app calls its grant allows, or the older operations that reach connected apps: source.* (except source.update_record), adapter.*, outbound_rails.*, product_analytics.*, transcripts.sync, autolog.*, perf_ads.sync_performance, mcp_servers.*, sync.completeness.run, sync.parity_check, crm.sync, connections.test, connections.preflight and connected_account.sync_now. They answer FORBIDDEN. An MCP or OAuth agent token with no key gets no connected apps at all. People and the built-in agents are not affected. Nothing is granted automatically, because that would widen what agents can reach without anyone deciding it. Read the operation log for the last weeks (audit.list as an owner or admin) to find the keys that used these operations, so you can grant them right after the upgrade.
  2. Set a real UNSUBSCRIBE_TOKEN_SECRET if yours is still the public default.
  3. Check where your organizations live. Organizations on a dedicated database (the database or instance tier) are not migrated by any upgrade path: gtm upgrade migrates the instance database only, so such an organization does not get the 0.3.0 migrations from it. An organization marked as schema tier whose data is still in the shared tables blocks the update; the updater names it and prints the one statement that fixes it.

Upgrade:

  1. Upgrade the CLI first.
    npm i -g @gtmos/cli@latest
  2. See what is available. This changes nothing.
    gtm upgrade --check
  3. Rehearse, then upgrade. Run from your instance folder, or pass --dir <path>.
    gtm upgrade --to 0.3.0 --dry-run
gtm upgrade --to 0.3.0 --yes

    gtm upgrade --channel stable follows the stable channel, which points at 0.3.0. A plain gtm upgrade never moves an install that is pinned to a version.

  4. Refresh your project files. In each project folder, run gtm init --refresh.

This release has 27 new migrations since 0.2.6, and every one only adds. One of them refreshes the installed copies of five first-party engine manifests in place. After the migrations, gtm upgrade brings every organization schema to the same shape as the shared tables, keeping every value.

After you upgrade:

  1. Set PUBLIC_CONSOLE_URL on the api service.
  2. Link the key. As an owner or admin, paste the project key in Integrations > Apps.
  3. Paste the verifier address from the Apps banner into the project's callback verifier setting, once.
  4. Connect old apps again. Apps made under the old sign-in are listed under relinkNeeded and must be connected again. Other existing connections are adopted automatically and keep working.
  5. Start again any connect that was half way through at the upgrade. It fails once on its return page. Start it again in Integrations > Apps.
  6. Set the webhook (integrations.webhook.subscribe) and a monthly limit for app calls.
  7. Give the agent keys you found their grants: a signed-in owner or admin runs agent.set_grants for each key (the key's id is in agent.list_keys). An outside agent that used an MCP or OAuth token needs an agent key, created in Integrations > Agents.
  8. SEO organizations: sign the three Search Console recipes (or keep the native Google token) and connect Ahrefs on your own account.
  9. Installations with several organizations that let owners use a private model endpoint: set GTMOS_CUSTOM_MODEL_PRIVATE=on on the api and worker services only if you accept that risk.

On first runs after the upgrade, a picker mapping makes one extra column listing call per run, an upsert signal that carried a free-mail domain is written once more, and existing organizations get a DRAFT motion proposed from their recorded blueprint choice, which changes nothing until a person approves it. The first data-quality scan can show a different duplicate count.

Going back to 0.2.6

Rolling back is an image swap only, with a check first.

gtm upgrade --rollback-check 0.2.6
gtm upgrade --rollback 0.2.6 --yes

The check is read-only and says whether you can go back. The rollback runs the check, stops the services, runs it again and only then swaps the images. Do not swap the images by hand. The check refuses while:

  • a connection type 0.2.6 does not know is in the shared tables (log_drain, perplexity, openai_compatible, profound, otterly, scrunch); it prints the command that removes them;
  • an organization is on the schema tier;
  • an app's records could be overwritten with another account's records. An app whose records were synced through two accounts on 0.3.0 cannot be synced safely by 0.2.6: stay on 0.3.0, restore the backup taken before the upgrade (losing every change made since), or disconnect that app for 0.2.6.

It also warns, without refusing, when approvals were archived on 0.3.0: 0.2.6 cannot open their history.

Check it worked

  1. gtm doctor shows the sources you expect as live.
  2. GET /health reports 0.3.0 on the API, worker, MCP server and console.
  3. The upgrade reported that verification passed, and a snapshot exists in your backups folder.
  4. Row counts of your main tables match the numbers you noted before.
  5. Integrations > Apps shows your connected apps, and the apps listed under relinkNeeded are connected again.

The full walkthrough is in the user guide.

Known limits

  • No live checks against real app accounts were run (see "Before you rely on it"). Packs and recipes stay beta until a live check passes.
  • Snowflake is held (not installable). A warehouse query the read stopped waiting for is not cancelled: it runs until the warehouse's own statement timeout.
  • Organizations on a dedicated database are not migrated by any upgrade path.
  • Privacy hiding is opt-in for source mappings. Only new installs of the Google Calendar, Gmail and Outlook packs mark their filters as privacy filters (and Gong's private calls). Existing installs and hand-written mappings keep their filters as they are until the pack is installed again or a new version is signed.
  • Privacy wins for a shared meeting: one member marking their copy private hides the title for every member. There is no "restore title" yet.
  • Changes the sync does not read are not seen: an event or e-mail that turns private outside the sync's read window, an Outlook event deleted from the calendar, and copies already sent outside GTM OS (alerts, webhooks, exports). A cancelled meeting is not hidden.
  • The shared call budget does not cover the CRM sync, the mailbox readers or the GEO vendor sources with your own key (their calls still count in the window). There is no instance-wide budget.
  • Gong and Calendly read one person per organization: a second installer replaces the first. The Gong pack keeps reading the installer's calls after they leave or lose their role, until an owner or admin removes or replaces it.
  • BigQuery reads at most 5000 companies a run and has no bytes-billed cap: set a daily query quota in Google Cloud. Leadfeeder visits are not linked to companies, and Webflow keeps only which form was sent and when.
  • Jira: one project per organization, the full read covers issues changed in the last 90 days, and there is no count check.
  • Xero: if the app returns its older date form, every changed-since read becomes a full read (more calls, nothing skipped).
  • Ads and CRM recipes: Meta Ads rows carry no conversions, Google Ads reads a fixed 30 days, Salesforce reads the 200 most recently changed records per object, and TikTok Ads has no recipe.
  • An agent cannot run the Semrush recipe. Approving a search content draft (SEO and GEO) still needs a second person in every workspace.
  • The verifier setting lives in your integrations project and GTM OS cannot read it, so the banner always says "Not verified".
  • The composio.* operation names answer as aliases for one release, for people only.
