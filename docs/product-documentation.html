01 · What GTM OS is

An operating system for go-to-market that you host and agents run.

GTM OS is an open-source, self-hosted platform that holds your go-to-market data in one typed model, runs the GTM work through engines, and lets humans and AI agents operate all of it through one governed interface where every customer-facing action waits for a second person to approve it.

7 engines 401 operations 35 canon object types 23 definition kinds 36 first-party packages 10 blueprints

For GTM teams

Most GTM teams run on a stack of tools that each hold a slice of the customer and none of which agree. GTM OS replaces that with one system: your accounts, contacts, deals, signals and activity live in one place, and the work on top of them (finding intent, enriching records, scoring accounts, routing, sequencing, SEO, paid ads) runs as engines you configure.

You describe your motion once (who your ICP is, which signals matter, how many emails a mailbox may send, who must never be contacted) and the engines follow it. Nothing reaches a customer, a CRM or an ad account until a person on your team approves it.

Under the hood

A small kernel holds the runtimes and the meta-model and contains no GTM business objects. Everything a company recognizes as GTM ships as packages on top (engines, ontology modules, connectors, screens, packs, blueprints). Every capability is an operation in one registry; REST, the TypeScript SDK, the gtm CLI and the MCP server are all generated from it and all call the same runOperation pipeline, so authorization and approvals cannot be bypassed.

Stack: Next.js console, NestJS API, Postgres with pgvector, Prisma, Better Auth, Cedar authorization, CEL expressions, a Postgres-native durable flow runtime, pnpm and Turborepo.

Who it is for

GTM engineers

The person who designs the scoring, routing, sequencing and data rules, usually working through Claude Code or Codex.

Revenue and marketing leaders

Owners and admins who approve sends, merges, budget changes and config before they go live.

Agencies

Teams that run GTM inside client orgs through delegations, with the client keeping approval rights.

The core idea

GTM OS is built so that an AI agent can do the work of a GTM engineer without being trusted blindly. The agent gets the same operations a human admin has. What it cannot do is approve its own work, widen its own authority, consent to OAuth in a browser, or switch off the safety switch. Those stay with people. In plain terms: the agent builds and proposes, a second human decides, and the kernel records who did what.

The README compares it to WordPress: a stable core you install on your own infrastructure, plus packages that deliver the work. You own the data and the deployment, and you can take your data out at any time with gtm org export.

How it is delivered

For GTM teams

What you get. A complete go-to-market workspace that runs on your own machine or cloud: a web console with your CRM (companies, contacts, deals), the engines that find, score, route and reach accounts, an approvals inbox, and a built-in agent workspace so Claude Code or Codex can set up and run the system with you. It is open source and self-hosted, so your pipeline data never sits in someone else's SaaS.

How you set it up. You do not configure it by hand. In an empty folder you open Claude Code and run gtm init, then /setup-gtmos. Claude installs GTM OS, creates your organization with an owner and a second approver, connects it to itself, and asks you only for the things a person has to provide:

  • your organization name and the two people's emails (the approver must be a different person);
  • one click on Connect Composio, after which the apps you already use (CRM, Gmail, Calendar, Slack, Search Console, Ahrefs) are discovered and linked;
  • the API keys you choose to add (an AI model, looot for data, an email sender), which you paste in the console;
  • the DNS records for your sending domain, if you will send email.

From setup to working system. Then /build-gtm-system: the agent interviews you about your ICP, offer, markets, channels and goals, proposes the engine settings, and builds them. You review and approve. When you are happy, one card in Environments > Go live signs everything and promotes it to production with a single approval. Expect roughly an hour for a first setup, most of it answering questions and approving.

Safe by default. A new install runs in live mode: anything not connected says so plainly and names the missing key, instead of showing invented numbers. Nothing is sent, merged or published without a person approving it, and the person who proposed a change (or whose agent did) can never approve it. A separate demo mode with sample data exists only for walkthroughs; never use it with real prospects.

Who does what. A GTM lead owns the decisions and approvals; the agent (or a GTM engineer) does the building; an IT person is only needed if you host it on company servers. Day to day, the team works in the console: the Hot list, company pages, outreach approvals and the engine dashboards.

What it costs to run. The software itself has no license fee. You pay only for what you connect: the AI model you choose, looot data credits for enrichment and signals (with per-run spend caps), your Composio plan, and the machine it runs on.

Staying current. New versions arrive as an upgrade command that snapshots your data first and rolls back automatically if anything fails. Your configuration, data and approvals history carry over.

Under the hood

Four images, gtmos-api, gtmos-console, gtmos-worker and gtmos-mcp (0.2.2), plus pgvector/pgvector:pg16, wired by a generated docker-compose.yml. Default ports: console 3000, API 3001, MCP 3004. The gtm CLI installs from npm (@gtmos/cli, 0.2.4 or later); the images are public on GHCR (ghcr.io/ay-automate/gtmos-{api,worker,mcp,console}, tags 0.2.2 and stable, linked to github.com/ay-automate/gtmos-releases), so gtm setup pulls them. Locally built images can still be used with --version <tag> --no-pull.

npm i -g @gtmos/cli
mkdir my-gtm && cd my-gtm && claude
! gtm init                      # agent workspace + docs, even with no instance yet
/setup-gtmos                    # Claude runs gtm setup, the agent key, connections

# by hand instead:
gtm setup ./instance --org Acme --email you@x.com --approver-email ops@x.com --version 0.2.2
gtm doctor --strict             # what is live, unverified, missing

gtm init writes CLAUDE.md at the project root, AGENTS.md, .mcp.json (the key is read from GTMOS_AGENT_TOKEN, never written to a file), the skills and commands, and docs/gtmos/ (reference generated from the live registry, plus the guides). GTMOS_LIVE=true is written into a new .env; --demo writes the keyless demo floor. Upgrades: gtm upgrade --check, then gtm upgrade --to <version> --dry-run and --yes (pin current images, pull, guard destructive migrations, snapshot, migrate inside the new image, health check, automatic rollback).

The kernel lives in kernel/*. It imports nothing from stdlib, and packages never get a raw database connection: the only database access goes through kernel stores under row-level security. CI enforces these boundaries with dependency-cruiser.

Packages

Everything installable is a package with a manifest (gtmos.package.yaml), declared permissions and one of three execution tiers. Install, enable, upgrade and rollback are proposals a second human approves. Details below.

Packages and execution tiers

For GTM teams

Think of packages as apps for your GTM system. Most are configuration only (a blueprint, a set of scoring rules, a screen layout) and carry no code at all. Packages that do carry code must be signed by a publisher the instance trusts, and third-party code runs in a sandbox that cannot touch your session or other data.

Under the hood

Ed25519 (or sigstore keyless) against the first-party key plus GTMOS_TRUSTED_PUBLISHER_KEYS. A trust ladder (community, verified, certified) grades versions; community runs only sandboxed and outside prod.

Package lifecycle operations: packages.install, packages.enable and packages.disable (per environment), packages.upgrade, packages.rollback, packages.uninstall, with packages.preview_upgrade as a read-only diff. The CLI mirrors them under gtm pkg, plus offline tooling to scaffold, validate, build (hash and SBOM) and sign.

The operation pipeline: an agent asks, a human decides

This is the path every call takes, whether it comes from the console, the CLI or an agent over MCP. A read runs straight through. A customer-facing effect stops at the gate and waits.

sequenceDiagram
  participant A as Agent

  participant K as runOperation
  participant G as Approval gate
  participant H as Second human
  A->>M: gtm_describe outreach.send_message

  M->>K: validate, org context, authz, guards

  G-->>A: approval id, state proposed

The pipeline stages, in order: validate the input against the operation's schema, resolve the org context, authorize (Cedar plus scope checks), run guards and transforms, compute the disposition (gate policy, Dry Mode, autonomy caps, lane controls, binding mode), create an approval if one is needed, execute, then write the outbox event and the audit record in the same org transaction.

03 · Core concepts

The ideas you need before anything else

Operations and their classes

For GTM teams

Every action in GTM OS has a name, such as score.score_account or outreach.send_message. Reading data is free to run. Writing your own data is logged. Anything a customer, a CRM or an ad platform would see is only proposed until someone approves it.

Under the hood

401 operations: 158 Q, 159 D, 5 T, 22 E, 57 M. Q runs as GET /v1/operations/<name>?input=<json>; the rest as POST /v1/operations/<name>. Each descriptor declares its class, input and output schema, required scopes and whether it needs approval.

Definitions

For GTM teams

A definition is one piece of your GTM playbook written down: an ICP segment, a persona, a scoring model, a sending lane, a play, a brand voice, a suppression rule. Engines read your definitions instead of hard-coded settings. Change the definition and the engine changes behavior, after review.

Under the hood

23 definition kinds plus 4 other config kinds (ontology.object, ontology.field, ontology.relationship, package.manifest). Each is a resource envelope (apiVersion, kind, metadata.key, spec) validated by a strict per-kind JSON Schema; unknown keys are rejected.

Lifecycle: draft, propose, sign, promote

A definition cannot be published straight into prod. It is drafted in dev through a ChangeSet, proposed for signing, signed by a human who did not propose it, then promoted. Engines read only the signed version in the call's environment; with none, they fall back to their stdlib default. Editing a definition creates a new version that must be signed again. definition.data_monitor is the one sign-exempt kind.

config.propose_changeset      -> draft ChangeSet         (gtm plan / gtm apply --env dev)
config.validate_changeset     -> issues, nothing applied
config.apply                  -> approval; a different human approves -> published in dev
definition.propose_for_signing-> proposed                (gtm definition propose-for-signing)
definition.sign_many          -> signed, by a human, not the proposer   (gtm definition sign-all)
env.promote dev -> prod       -> ONE approval            (gtm promote --all dev prod)

Environments

For GTM teams

Every org has three spaces: dev to build, staging to check, prod where things run for real. Emails sent from dev or staging go to a sink and never reach anyone. The console shows a banner ("N definitions are in dev, not live") until you sign and promote.

Under the hood

prod is the default for MCP and REST calls that name no environment. MCP takes an environment argument or the x-gtmos-environment header; an unknown key is refused. env.promote plans every changed resource, proposes one approval and walks dev → staging → prod; backward is refused. config.promotion_status reports what is not live.

Approvals and four-eyes

The four-eyes rule. The person or agent who proposed an action cannot approve it, sign it or execute it. Neither can the human an agent acts for. An agent cannot approve anything at all. Only an owner or admin can approve. The proposer can still withdraw a proposal, and any approver can reject (veto) it.

For GTM teams

Every send, CRM write-back, record merge, page publish, ad budget change and config change that goes live lands in Approvals or Needs a human. A teammate reviews it, approves, then executes. If your org has only one admin, nothing can go live: add a second approver first.

Under the hood

An E-class call creates an ActionApproval in state proposed. States: proposed, approved, rejected, withdrawn, revoked, expired (after 7 days), executing, executed, failed. Ops: runtime.approve_action, runtime.reject_action, runtime.execute_approval, runtime.withdraw_action. At execution the gate re-checks that a valid, distinct human approver is stored. Actions auto-approved by a gate policy or a pre-approval envelope are exempt: the standing rule is their approver.

Dry Mode

An org-wide safety switch (Settings > Safety, policy.set_dry_mode, human only). While it is on, every E-class operation becomes a draft: logged, never executed, no approval created. D, T and M operations still run. Every console page shows a banner. Read it with policy.get_dry_mode.

Provenance and lineage

Every value on a record knows where it came from: the winning observation, the others that competed, the survivorship rule, a confidence from 0 to 1, a band (VERIFIED, PROBABLE, POSSIBLE) and a status. A human edit is VERIFIED and automation never overwrites it. Read it with records.provenance and lineage.trace (MCP gtm_lineage_trace); the CRM record pages show a provenance panel.

Readiness and required connections

instance.readiness (CLI gtm doctor) lists every seam with a status: live, configured_unverified, failed, fixture or not_configured. Items are required while the engine that needs them is in use, otherwise informational. Applying a blueprint makes its declared connections required. The console shows the same list as Required connections on Integrations > Connections.

04 · Ontology and data

One model of your market

For GTM teams

The ontology is the shared vocabulary every engine uses: accounts, contacts, deals, signals, activities and more. Your CRM data, enrichment results, form fills and intent data all land on the same records. You can add your own fields (an account tier, a product line) and your own objects (partners, projects) without waiting for a release.

Under the hood

35 canon object types in the reserved gtm.* namespace (ontology 0.1.0-draft), interfaces Subject, Engageable, Touch, Monetary, and stage machines such as gtm.pipeline.deal_stage. Every object carries common fields (id, revision, timestamps, owner_principal_id, archived_at, a custom JSON bag). Live list: query.object_types.

Custom fields and custom objects at runtime

For GTM teams

Add a field to companies, contacts or deals in Settings > Custom fields: text, number, date, checkbox, select, URL, email, phone or user. It appears in tables and filters at once. A new object type (say, "Partner") is designed in CRM > Model and goes live after a second person approves it.

Under the hood

Fields: field.create (no approval, owner/admin or their agent with engine.configure), plus field.update, field.archive, field.coverage, field.backfill. Objects: ontology.propose_changeset with create_object, add_field, add_relationship (keys custom.<slug>), ontology.validate_changeset, then ontology.publish_changeset (human only, approval). Canon fields can be extended, never redefined.

Identity resolution

Two layers keep one record per real company and person.

  1. Observation to entity (data plane). An account matches on domain (authoritative) and name (corroborating); a contact on primaryEmail and displayName. Matching runs deterministic, then blocking, then probabilistic; unsafe matches go to a human review (resolve.review.decide). A signed definition.identity_rule overrides the keys and survivorship (most_recent, highest_confidence, first_write_wins, longest_non_empty, source_priority).
  2. Record dedupe (Identity & DQ engine). identity_dq.scan_duplicates, then identity_dq.merge_records as an approval, reversible with identity_dq.unmerge_records.

Automated writes onto an existing record must resolve to that record by domain, email or source id. A write that cannot resolve never creates a duplicate; source mappings report it as unresolved.

Vectors and search

search_records (MCP) fuses Postgres full-text rank with pgvector similarity over accounts, contacts, deals and activities. Embeddings come from OpenAI (text-embedding-3-small) or Gemini (gemini-embedding-001), whichever key the org has. Anthropic has no embedding model; without OpenAI or Gemini, results come back mode: "text_only". Indexing runs as a daily background sweep; search.index_status shows coverage and search.reindex_now runs it on demand.

The CRM

For GTM teams

The console includes a full CRM: Hot list, Companies, Contacts, Deals with managed pipelines and stage moves, Tasks, a timeline per record, saved and shared list views, CSV import, a Data quality page, AI chat, Sequences and Research. It can be your system of record, or mirror the CRM you already use.

Under the hood

CRM screens live in apps/console under /org/<orgId>/. Writes: canon.edit / canon.edit_many for canon objects (an agent's call becomes a proposal), records.create for custom objects, canon.import (max 1000 rows per call), deal.move_stage, deal.close, pipeline.create, view.create, task.create. Reporting currency and FX conversion for deals shipped in 0.2.1.

05 · The engines

What does the work

Seven engine packages ship and are installed for every org. Around them sit routing, plays, the research agent, CRM sync, source mappings, the search index and agent chat. Every engine runs on your signed definitions in the call's environment and falls back to a stdlib default. Build in this order: data first, then scoring, then routing and plays, then the outbound channels.

Signals and intent

stdlib/engine.signals 1.0.0

For GTM teams

Captures the reasons to reach out: funding, hiring, expansion, a pricing-page visit, a booked call, an intent-topic surge. Each signal gets a strength that fades over time, so last month's funding round counts less than this week's. Accounts above your thresholds become hot or warm.

Under the hood

Records typed gtm.signal rows (idempotent, 1 to 1000 per call), computes recency-weighted strength (default half-life 30 days, hot at 60, warm at 30) and surge reports. Intent comes from looot capabilities such as intent.topic_surge and intent.visitor_identification.

Scoring and qualification (Hot list)

stdlib/engine.score 0.1.0 · stdlib/qualification

For GTM teams

Decides which accounts deserve attention now. It combines two views: fit (does this company match your ICP by region, size, industry) and intent (are they showing buying signals). Each verdict comes with the evidence behind it, and qualified accounts appear on the Hot list.

Under the hood

Rule-based scoring of gtm.signal against a versioned policy, producing gtm.qualification. Key default scores intent (default score.default.v1: qualified ≥ 60, review ≥ 30); key icp_fit matches the synthetic firmographic kind with CEL conditions over account fields. The stdlib icp_fit fallback is a pilot hypothesis: always sign your own.

How the pieces move together

From signal to approved send

This is the default path with both workflow flags on (signals.reaction, qualification.handoff). No custom play is needed.

flowchart TD

07 · Integrations

What GTM OS connects to, and why

The split that matters. looot is for buying third-party data. Composio is for your own apps and actions in them. Never use Composio to buy data, and never use looot to write into your CRM.

looot: third-party data

For GTM teams

The single source for outside data: company and people search, lookalikes, email and phone finding and verification, intent, news, jobs, web search, page extraction and SEO keyword data. Every call is priced, capped and recorded with its source.

Under the hood

Reached only through capabilities (capability.quote, capability.acquire) resolved by a definition.binding with backend: looot; there are no looot.* operations. Credential: instance LOOOT_TOKEN or a per-org looot Connection. Values carry provenance looot:<capability>:<runId>. Pin an endpoint with gtm capabilities discover.

Composio: your own apps and actions

For GTM teams

Composio connects GTM OS to the SaaS accounts you already use, from a catalog of 1,000+ toolkits: your CRM, Slack, Typeform, Stripe, Ahrefs, Search Console and more. Click Connect Composio, sign in, and apps you already connected in Composio are picked up automatically.

Under the hood

Three credential modes, one per org (the newest replaces the previous): Connect Composio (OAuth 2.1 + PKCE, tokens sealed and refreshed: composio.oauth_start → composio.oauth_callback), a ck_ Connect key, or an ak_ project key (composio.set_api_key, verified live). uak_ user keys are refused. Precedence: sign-in, then ck_, then ak_, then instance COMPOSIO_API_KEY. Auto-discovery: composio.sync_connections; status: composio.status.

Per-org MCP servers

Any streamable-HTTP MCP server can become a capability backend for one org, without a restart. mcp_servers.add stores the URL and auth header sealed, mcp_servers.test runs a live initialize and tools/list, and a human marks each tool read or write with mcp_servers.set_tool_effects. Bind it with definition.binding {backend: "mcp", opId: "mcp:<server>:<tool>"}. An undeclared tool is unusable; a write tool needs riskClass: "high_risk", broker.accept_high_risk and a second human's approval on every call.

08 · Flexibility and customization

Change almost anything, through an agent, under review

GTM OS is designed so that you, through Claude Code, Codex or any MCP agent, can reshape the system to fit your motion. Engines, data model, data sources, integrations, starting templates, packages and screens are all configuration. The agent writes it; your team signs it; it goes live.

For GTM teams

You do not file a feature request to change how leads are scored or which accounts get a sequence. You tell the agent what you want ("weight hiring signals higher, and only DACH companies with 200 to 5,000 people"). It writes the definition in dev, shows you the diff, and a teammate signs it. The same goes for a new field, a new object, a new data source or a new automation.

Under the hood

Every customization point is an operation or a definition kind with a strict schema, so the agent never guesses a field (gtm_describe returns the exact JSON Schema). Config changes travel as ChangeSets, are validated before anything applies, and go through the same sign and promote path as anything else. Nothing is edited in the database directly.

What you can customize

Engines

Scoring models and thresholds (definition.scoring_model), buying committees, segments, personas, lanes (caps, checks, budget, domain), sequences, brand voice, suppression and compliance, unit economics, workflow flags (qualification.handoff, signals.reaction, identity_dq.thresholds) and routing owners.

Ontology

Custom fields on accounts, contacts and deals (field.create, immediate). Custom objects and relationships (ontology.propose_changeset, published after approval). Optional modules such as stdlib/gtm.partner. Pipelines and stages.

Data

Source mappings from any Composio app or MCP server into any canon or custom object, with transforms, match keys, schedule and optional gated write-back. Identity rules and survivorship. Mirror modes per object type. CSV import.

Integrations

Connect any Composio app; add your own MCP servers; bind any capability to looot, Composio, MCP or native backends with a price cap and fallbacks (definition.binding). Build Composio-powered automations as plays whose steps call operations, or as agents with triggers.

Blueprints

Start from the closest general blueprint (blueprint.apply), then change only what your motion needs. Blueprints are general templates: no customer-specific blueprint ships, and you should not create one.

Packages

Ship your standard setup as a declarative package of definitions and parameters (gtm pkg scaffold --tier declarative). Code goes in a signed trusted or sandboxed package. Example: examples/acme-cyber-outbound/.

Apps and screens

Declarative screens with definition.app (routes, audiences, pages composed from view types over operations), served at /org/<org>/a/<key>. Sandboxed code apps for custom UI. Console theme tokens via definition.brand_kit. Saved views and nav settings per org.

Agents and automations

Register agents with a signed definition.agent (scopes, skills, step, cost and deadline bounds), and fire them manually, on a schedule or on CRM events (agent.trigger.create). Long jobs run as missions with one human approval moment.

Agent parity

An agent key with the Full GTM engineer preset (the Claude Code default), acting for an owner or admin, can do everything that person can do in the console through operations: records, fields, pipelines, definitions (proposed), research settings, CRM settings, workflow flags, connections and keys the user hands over, MCP servers, syncs, scans. 09 · Security and governance

Who can see, do and approve what

For GTM teams

Each organization's data is walled off from every other organization at the database level. API keys and OAuth tokens are encrypted and never shown again after you save them. Every action, by a person or an agent, is written to a tamper-evident audit log with who proposed it, which agent did it, for whom, and who approved it.

Under the hood

Every tenant table is under Postgres row-level security and the app connects as a non-superuser NOBYPASSRLS role. Credentials are AES-256-GCM encrypted under a per-org data key (envelope encryption), rotatable with secret.rotate_org_key. The operation audit log is hash-chained per org with signed daily checkpoints.

Sign-in

Better Auth sessions, Google and Microsoft sign-in, SSO (sso.*) and allow-listed sign-in (auth.allowlist.*), all human-only to configure.

Sandboxing
